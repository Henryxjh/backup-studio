## 1. 需求分析（辩证）

### 1.1 需求合理之处

原始需求的六个要点——独立入口按键、新页面、选目录后检测、哈希重复与同名重复分列、逐条「保留/删除/下次不提醒」、双击路径打开所在目录——构成一个**边界清晰、可验收、不依赖云端**的本地工具，方向正确：

1. **问题真实且高频**。同一批文件反复备份、下载目录重复下载、照片多次导入，是「重复占空间」的主要来源；这类问题目前在本项目里**完全没有出口**——备份引擎只负责把源端镜像到目标端，不回答「目标端里哪一份是多余的」。
2. **与本项目定位同向**。本项目已经是「内容哈希去重」的专家（`planner.ts` 五轮收敛判定），重复文件检测是同一套内容指纹能力的**另一种用法**，而非新造轮子。
3. **只读扫描 + 明确动作**，天然契合本项目「默认只读、写入须可解释」的立场：检测阶段零写副作用，删除阶段才进入写路径。
4. **入口独立、页面独立**，避免把「清理」语义混进「备份」主线，降低误操作风险。

### 1.2 必须澄清和补强的点

原始描述有八处含糊或缺口，若不补强，实现出来会是一个「看起来能用、实际危险」的工具：

| # | 含糊点 | 风险 | 补强方向 |
| --- | --- | --- | --- |
| 1 | 「删除」没说是永久删除还是可撤销 | 不可逆丢数据 | 落系统回收站 + 删除前二次校验（§12.1 已定版） |
| 2 | 「重名但不重哈希」与「哈希重复」的操作强度没有区别 | 用户把「同名不同内容」当重复删掉，丢的是**不同的内容** | 两类分开呈现，重名类整页告警、默认不预选任何删除项（§12.1 已定版） |
| 3 | 「下次不提醒」的作用对象没定义 | 抑制过度，重复文件永久消失 | 以**内容哈希**为键入黑名单，作用域默认当前扫描根，可撤销（§12.1 已定版） |
| 4 | 「撤销下次不提醒」的入口没位置 | 功能等于不可用 | 页面顶部工具栏常驻「抑制清单 (N)」，逐条撤销 + 全部撤销（§6 FR-13） |
| 5 | 判定算法未指定 | 全盘哈希 = 全盘读，几十万文件会拖垮磁盘 | 三级漏斗：size 分桶 → 首尾 64 KiB 局部哈希 → 全量 SHA-256（§6 FR-03） |
| 6 | 「重名」的同名范围未定义 | `报告.pdf` 与 `报告.pdf`、跨目录同名全算冲突，噪声巨大 | 同名按**目录内同名**判定，跨目录同名不进本类（§5 术语） |
| 7 | 删除与备份引擎并发无约束 | 删除正在被同步的文件，破坏 manifest 与断点 | 删除期间与备份/自动同步互斥（§6 FR-10） |
| 8 | 删除动作未纳入容灾闸门 | 介质掉线/隔离期间仍执行删除 | 删除属写操作，复用 `service.writeGate()`（§6 FR-10） |

### 1.3 建议默认策略

以下为分析得出的默认建议，其中四条已由用户定版（§12.1），其余为实现默认值，可按需调整：

- **判定用三级漏斗**，不追求「一次算到底」：先按大小分桶（零 I/O）淘汰 80%–95% 的文件，再对同桶候选算哈希。
- **大文件不假装确定**：超过阈值的文件跳过全量校验，标注「疑似重复（未全量校验）」，与确定结果分开展示。
- **每组至少保留一份**，是硬约束，不可由任何批量动作绕过。
- **删除前二次校验**：重算哈希并比对大小与文件身份，扫描后被改动的一律跳过并明确提示。
- **删除进系统回收站**，跨平台降级为本机隔离区（可还原），任何情况下不提供「一键永久删除」。
- **同名不同内容类默认不预选**，需要人工逐条或显式批量确认。
- **抑制以内容哈希为键**，默认作用域为当前扫描根，避免在 A 目录抑制的内容在 B 目录被一并隐藏。
- **近似重复（感知哈希）本期不做**，留作 P1 储备（§4.2）。

### 1.4 定版结论（用户已确认）

| 决策项 | 定版结果 |
| --- | --- |
| 删除落地方式 | **系统回收站 + 删除前二次校验**（B+C 组合） |
| 重名不同内容类默认动作 | **不预选任何删除项，整页告警** |
| 「下次不提醒」 | **内容哈希黑名单**；命中项下次扫描跳过；**撤销单独一个按钮**，位置由本规划决定（§6 FR-13） |
| 近似重复（pHash） | **本期不纳入**，列为 P1 储备 |

## 2. 竞品与大厂逻辑调研

> 调研目的：确定判定流水线、保留/删除策略、同名冲突的呈现方式、抑制与撤销的交互范式，避免自造一套与行业惯例相悖的语义。
> 下列结论均来自公开可查的产品行为与官方文档；本项目只借鉴**文件级**语义，不引入块级去重（见 §2.6）。

### 2.1 判定流水线：三级漏斗是行业共识

| 层级 | 手段 | 收益 | 行业做法 |
| --- | --- | --- | --- |
| 1 | 按**文件大小**分桶 | 零 I/O（size 在选文件时已有），可淘汰 80%–95% 的候选 | Czkawka、dupeGuru、Deskora、TreeMap 均以此为第一级；Deskora 直接取 NTFS 索引的 size，做到零磁盘读 |
| 2 | 同桶候选只读**首尾各 64 KiB** 算局部哈希 | 只读 128 KiB 淘汰绝大多数「同大小不同内容」 | 主流查重工具的通用做法；选「首+尾」而非「连续前 128 KiB」，因为格式签名集中在头部、索引与收尾结构集中在尾部，差异密度更高 |
| 3 | 仍相同才做**全量 SHA-256** | 读取量收敛到极少数候选组 | 全量哈希只在最后一级使用 |

补充约束：局部哈希相同的**大文件**不再全量校验，而是标注「疑似重复（未全量校验）」，不与确定结果混排——这是查重工具的诚信红线。

### 2.2 保留与删除策略

| 经验 | 来源 | 对本项目的映射 |
| --- | --- | --- |
| **每组至少保留一个文件**，任何规则组合都不能清空一组 | Bytesweep | FR-11 硬约束 |
| 「Keep This, Delete Rest」：保留指定一份，其余归入清理列表 | Google Photos | 组级动作 FR-07 |
| 合并时保留**质量最高**的一份，其余移入「最近删除」（30 天） | Apple iOS 18「重复项目」 | 组级保留 + 可撤销删除 FR-08 |
| 重复文件**只进回收站**，不提供一键批量永久删除 | Deskora | FR-08 只提供回收站落地 |
| 清理项在同盘保留 **7 天**，可逐项还原 | Bytesweep | 跨平台降级方案（§6 FR-08） |
| **删除前二次校验**：重算哈希比对内容签名，扫描后变更则跳过，候选变成链接也跳过 | C Cleaner Plus | FR-09 |
| 保留规则可配置：保留最新 / 最旧 / 最大 / 最短路径；**保留「像原件的那份」**（优先归档目录、避免「副本 (1)」这类命名） | Bytesweep | 组级默认保留规则 FR-07（默认保留「路径不含副本标记 + 修改时间最早」的一份） |
| 硬链接替代删除：把多余副本换成硬链接，省空间但不删文件 | Czkawka | 列为 P2 储备（§4.2） |

### 2.3 同名不同内容：行业一致选择「保留双方 + 冲突副本重命名」

这是本需求第二类（重名但内容不同）与第一类（哈希相同）必须区别对待的直接依据：

| 产品 | 冲突副本命名 | 关键行为 |
| --- | --- | --- |
| Google Drive | `文件名 (conflicted copy from 设备名 on 日期).ext` | 保留原件 + 生成冲突副本，**不覆盖任何一方** |
| OneDrive | `文件名-计算机名.ext` | 同上；另保留最多 5 个冲突版本 |
| Dropbox | `文件名 (用户 的 conflicted copy 日期).ext` | 同上 |
| Box | `文件名 (conflict – 日期).ext` | 同上 |
| Syncthing | `.sync-conflict` 副本 | 同上，并提供版本历史兜底 |

共同点：**冲突是保守合并，不是损坏**；判定责任交回用户（对比 → 合并 → 重命名 → 归档）。四个产品都被实测验证为「不会静默销毁双方编辑」。

对本项目的映射：重名不同内容类**必须整页告警、默认不预选删除项**，任何删除都要显式确认；并且**必须展示两组内容的差异证据**（大小、mtime、哈希短指纹），让用户能自己判断，而不是让工具替用户判断。

### 2.4 抑制与撤销：抑制必须可回溯、可撤销

| 产品 | 做法 | 对本项目的映射 |
| --- | --- | --- |
| Windows Defender | 「排除项」+「保护历史记录」，被隔离项可逐条还原 | 抑制清单必须**可查、可逐条撤销**，而非只有一个全局开关 |
| Czkawka | 默认排除集（回收站、`.git`、`node_modules`），且排除项在「删除/移动/硬链接」时被自动绕开 | 抑制项必须在**执行删除动作时同样生效**，否则会出现「提示时跳过、删除时却删掉」的矛盾 |
| 百度网盘 | 「扫描重复文件 → 智能选择 → 快速清理」；另有同步参数「取消文件重复」与「关闭提醒」开关 | 国内产品的抑制**缺少可回溯清单**，用户误关后无从恢复——这正是本项目要补的短板 |

### 2.5 近似重复（感知哈希）

| 产品 | 手段 |
| --- | --- |
| Apple iOS 18 | 感知哈希 + 内容哈希识别裁剪、调亮后的相似照片，合并时保留最佳版本 |
| Google Photos | 自动堆叠相似照片并设「Top Pick」，支持「Keep This, Delete Rest」 |
| Czkawka | Blockhash / Mean / Gradient，相似度阈值 0–40 |

本项目本期不纳入（§4.2），但设计上要为它留位：分组结构须能承载「相似度」维度，而不只是「相同/不同」二值。

### 2.6 调研结论对本项目的取舍

- **借鉴**：三级漏斗、疑似标注、每组留一份、回收站落地、删前二次校验、冲突副本的保守语义、抑制可撤销。
- **不借鉴**：块级去重。Windows Server Data Dedup、Google Cloud Storage、Dropbox Magic Pocket 都是**块级**（32–128 KiB 分块 + 指纹索引 + reparse point/块存），面向存储层，收益是省空间、代价是碎片化与还原变慢。本项目是**文件级**工具，用户预期是「找出多余的那份文件并处理掉」，两者语义不同，强行混用会让「保留/删除」的直觉失效。
- **不借鉴**：自动合并冲突内容。云盘自己都不做二进制自动合并（只对 Office 文档提供应用内合并），本项目更不应替用户决定「留哪份」。

## 3. 背景与目标

**背景**

Backup Studio 解决的是「把源端可靠地镜像到目标端」。但在真实使用中，目标端（尤其是被反复同步过的目录、备份的备份、照片多轮导入）会积累大量内容完全相同的副本，源端一份、目标端 N 份。当前软件对此**完全无感知**：备份引擎的去重只发生在「源端 ↔ 目标端」配对时，目标是目标端已有的孤儿副本从不会被提示。

**目标**

- 用户选一个目录，得到一份可信的重复文件清单：**哈希相同者**归为一类，**同名但内容不同者**归为另一类并重点提示。
- 每一项都有明确动作：**保留 / 删除 / 下次不提醒**；删除可撤销；抑制可撤销。
- 检测过程对磁盘友好（分级判定，不做无谓的全盘读），对用户诚实（不确定就标「疑似」，不伪装确定）。
- 任何删除动作都受本项目既有的**统一写入闸门**与**备份引擎互斥**约束，介质异常或备份进行中一律不删。

**非目标**

- 不做块级去重、不做存储层优化。
- 不做近似重复（感知哈希）识别（本期）。
- 不做跨目录的同名冲突治理（本期只做目录内同名）。
- 不做文件内容自动合并、不做自动决定「留哪份」。
- 不提供任何形式的「一键永久删除」。

## 4. 范围

### 4.1 包含

- 标题栏**独立按键** → 进入**全屏独立页面**「重复文件检测」（主界面为备份主线，检测页为独立视图）。
- 选一个目录 → 递归扫描 → 三级判定 → 分两类展示结果。
- 类别一 **内容重复（哈希相同）**：不论文件名是否相同，一律归入此类。
- 类别二 **同名但内容不同**：单独成区，整页告警，明确写出「同名不代表内容相同」。
- 每条结果的动作：**保留 / 删除 / 下次不提醒**；组级动作：**保留此份（其余可删）/ 整组不再提醒**。
- **系统回收站**落地 + **删除前二次校验**。
- **内容哈希黑名单**（下次不提醒）+ 页面顶部**「抑制清单 (N)」**入口与撤销按钮。
- 双击结果中的**文件绝对路径** → 在系统文件管理器中定位该文件所在目录。
- 扫描进度、随时取消、结果虚拟滚动、可回收空间统计、操作审计日志。

### 4.2 不包含

| 项 | 理由 | 计划 |
| --- | --- | --- |
| 感知哈希近似重复（裁剪/调亮后的相似图） | 需图像解码依赖，与「零第三方依赖」冲突，误判风险高于收益 | P1 储备（§4.3） |
| 硬链接替代删除 | 跨平台语义差异大（Windows 需管理员权限），收益有限 | P2 储备 |
| 重复**文件夹**检测（内容相同的目录树） | 与文件级判定重叠，边界难定义 | P2 储备 |
| 跨目录同名冲突治理 | 噪声大，需先定义「同目录」的判定边界 | P1 储备 |
| 云端/网络盘的重复文件 | 需要下载，占位文件无法比对 | 不做（明确声明） |
| 与备份引擎的自动联动（备份时顺带查重） | 改变备份主线的语义与性能 | 不做 |

### 4.3 后续储备（设计预留，不在本期实现）

- **P1 近似重复**：分组结构需预留「相似度」维度；届时以感知哈希（如 64 位 dHash）对图片/视频分组，阈值可调，与「确定重复」分栏展示。
- **P2 硬链接**：把多余副本替换为硬链接，保留路径、释放空间。
- **P2 重复文件夹**：按目录树内容指纹识别整棵重复目录。

## 5. 术语

| 术语 | 定义 |
| --- | --- |
| **内容重复** | 两个及以上文件的内容哈希（SHA-256）完全相同，**与文件名是否相同无关**。本需求的第一类结果。 |
| **同名不同内容** | 同一目录内存在同名文件，但两者的内容哈希不同。**同名不构成重复**——它们是两份不同的数据。本需求的第二类结果。 |
| **同名（判定范围）** | 仅指**同一父目录内**的文件名相同（大小写按文件系统语义比较）。跨目录同名文件**不**归入第二类，也不视为重复。 |
| **组** | 一组内容互为重复的文件，共享同一个内容哈希；或一组同名但内容互不相同的文件。 |
| **组主（推荐保留项）** | 组内默认建议保留的那一份，见 §6 FR-07 的默认规则。 |
| **抑制（黑名单）** | 用户选择「下次不提醒」后记录的内容哈希。后续扫描命中该哈希时跳过整组，不再提示。 |
| **抑制清单** | 已记录的全部抑制项列表，支持逐条撤销与全部撤销。 |
| **疑似重复** | 大文件跳过了全量校验，仅凭「大小 + 首尾局部哈希」判定，**不保证**内容完全一致。 |
| **回收站落地** | 删除动作把文件移入系统回收站（Windows/macOS/Linux），而非永久删除。 |
| **本机隔离区** | 系统回收站不可用时的降级目标：本机 `userData` 下的隔离目录，同样可还原（§6 FR-08）。 |

## 6. 功能需求

| FR | 名称 | 优先级 | 状态 |
| --- | --- | --- | --- |

### 6.1 入口与页面

**FR-01 独立入口按键与独立页面（P0）**

- 标题栏新增**独立按键**「重复文件检测」，不与备份主线的「目录 / 计划 / 执行」三步骤混排。
- 点击后进入**全屏独立页面**；页面顶部提供返回按键，回到备份主界面。
- 页面切换不依赖路由库（当前渲染层无路由依赖），由 `App.tsx` 的视图状态切换实现。
- 页面自身拥有独立状态机（§7），与备份任务的状态互不污染，但受 FR-10 的互斥约束。
- **验收**：从主界面点击按键进入检测页；检测页可返回；切换过程中备份主界面的计划与进度不丢失。

**FR-02 目录选择与扫描范围（P0）**

- 复用现有目录选择框（`pickDirectory`），标题为「选择要检测重复文件的目录」。
- 递归扫描子目录；**跳过符号链接**（不跟随，避免成环与跨盘）。
- **跳过 0 字节文件**（内容必然相同，成组无清理价值），并在结果中报告跳过数量。
- 默认最小文件尺寸 **1 KiB**（可调），低于阈值的文件不参与分组。
- 默认排除本软件自身的元数据目录 `.backup-studio`。
- 检测目录**不需要**与备份的源/目标目录绑定；用户可以检测任意目录。
- **验收**：选择含子目录的目录，扫描结果包含子目录文件；符号链接不产生重复项；0 字节文件被跳过且计数可见。

### 6.2 判定

**FR-03 三级判定流水线（P0）**

判定按「代价由低到高」三级推进，每级淘汰后不再进入下一级：

1. **按大小分桶（零 I/O）**：size 唯一的文件直接出局，不读一个字节。
2. **首尾 64 KiB 局部哈希**：仅对同桶候选计算；读取首 64 KiB 与尾 64 KiB，拼接后算 SHA-256。
3. **全量 SHA-256**：仅对局部哈希仍相同的候选计算。

附加规则：

- 单文件超过 **256 MiB** 时**跳过全量校验**，标记为「疑似重复（未全量校验）」，与确定结果分栏展示，不得混入确定结果。
- 哈希算法固定为 **SHA-256**，复用现有 `electron/engine/hash.ts` 的并发实现（并发数 `2..8`，随 CPU 自适应）。
- **扫描与哈希只读**：检测阶段不得对被检测目录产生任何写副作用。
- **验收**：同一目录内唯一大小的文件不产生任何读取；同大小不同内容的文件在第 2 级被淘汰；大文件出现在「疑似」区而非确定区。

**FR-04 内容重复分组（P0）**

- 哈希相同的文件归为**同一组**，**不论文件名是否相同**；跨目录的同哈希文件同样归入一组。
- 每组展示：短哈希指纹（SHA-256 前 8 位十六进制）、文件份数、单份大小、**可回收空间 = (份数 − 1) × 单份大小**、组内每一条的**绝对路径**。
- 组内每条额外展示：文件名、大小、修改时间。
- **验收**：内容相同但文件名不同的两个文件出现在同一组；同名的同哈希文件也只出现在这一类，不重复出现在第二类。

**FR-05 同名不同内容分组与告警（P0）**

- 判定范围：**同一父目录内**同名、且两两内容哈希不同。
- 结果**单独成区**，与「内容重复」区物理分离，不混排。
- 该区顶部**固定告警条**，文案须明确表达：**「同名不等于重复：这些文件内容不同，删除任意一份都会丢失独有内容。」**
- 该区**默认不预选任何删除项**，任何删除都必须由用户显式发起（逐条或显式批量）。
- 每组须展示差异证据：两份的大小、修改时间、哈希短指纹，供用户自行判断。
- **验收**：同目录内 `a.txt` 两份内容不同 → 出现在第二区且带告警；该区无任何默认勾选；跨目录同名文件不进入该区。

### 6.3 动作

**FR-06 逐条动作（P0）**

每条结果提供三个互斥动作按钮：

| 动作 | 语义 | 结果 |
| --- | --- | --- |
| **保留** | 保留此份 | 本条标记为保留，从删除候选中排除；若组内其余全部已保留则该组不再有可删项 |
| **删除** | 删除此份 | 进入待删队列，执行前须通过 FR-09 二次校验与 FR-10 闸门 |
| **下次不提醒** | 本组不再提示 | 该组内容哈希写入抑制黑名单（FR-12），下次扫描跳过整组 |

- 动作**仅在本次会话内作用于列表状态**，持久化只保存抑制项与审计日志。
- 「删除」在待删队列中**可撤销**（未执行前可取消勾选）。
- **验收**：三动作互斥且即时反映在列表与可回收空间统计中。

**FR-07 组级动作与默认保留规则（P1）**

- 组级动作两个：**「保留此份，其余可删」**（把组内指定一份标为保留，其余加入待删队列）与 **「整组不再提醒」**（等价于对组内任一条执行「下次不提醒」）。
- 默认**组主（推荐保留项）**选取规则，按优先级：
  1. 文件名不含副本标记（`(1)`、`副本`、`copy`、`Copy`、` - Copy`）者优先；
  2. 修改时间**最早**者优先（副本的 mtime 通常等于复制时间，晚于原件）；
  3. 路径最短者优先；
  4. 路径字典序兜底。
- 组主仅是**建议**，界面明确标注为「建议保留」，不自动执行删除。
- **验收**：组内「副本 (1)」文件不会被选为组主；组主仅标注不自动删除。

**FR-08 删除落地：系统回收站 + 降级隔离区（P0）**

- 删除**一律不进永久删除**：优先移入**系统回收站**（Windows 资源管理器回收站 / macOS 废纸篓 / Linux 回收站）。
- 系统回收站不可用（Linux 未提供 trash 实现、网络盘、只读卷）时，降级为**本机隔离区**：移动到本机 `userData` 下的隔离目录，保留原路径映射，**可还原**。
- 降级发生时必须在界面**明确告知**：目标为「本机隔离区」而非「系统回收站」，并给出还原入口。
- 任何情况下**不提供**「永久删除」按钮，不提供「跳过回收站」开关。
- **验收**：删除后文件在系统回收站可见；回收站不可用时文件进入隔离区且可还原；界面无任何永久删除入口。

**FR-09 删除前二次校验（P0）**

执行删除前，对**每一个**待删文件重新校验：

1. 重新计算内容哈希，与扫描时记录的哈希比对；
2. 比对文件大小；
3. 校验文件身份（`dev`/`ino`），排除「扫描后被替换成另一个文件」的情况。

任一项不匹配 → **跳过该文件**，在结果中标注「扫描后已变更，已跳过」，不删除、不报错终止。全部待删文件的校验与删除动作逐条独立，某条失败不影响其余。

- **验收**：扫描后修改文件内容 → 该文件被跳过且有明确提示；删除的其余文件照常完成。

**FR-10 写入闸门与备份互斥（P0）**

- 删除是**写操作**，必须经过与备份引擎同一个 `service.writeGate()` 裁决：介质不可达、隔离观察中、L2、磁盘只读、卷需修复、卷健康无法判定 → **一律拒绝删除**，并展示阻断原因。
- 备份任务或自动同步**正在运行**时，检测页的删除动作**禁用**并给出原因提示（不得并发删除正在被同步的文件）。
- 检测页的删除**不**反向触发备份引擎的 manifest 更新；被删除的文件在下次备份对账时按孤儿文件处理（走既有规则）。
- **验收**：介质处于 L2/隔离/不可达时点击删除被拒并说明原因；备份运行中删除按钮不可用。

**FR-11 每组至少保留一份（硬约束）（P0）**

- 任何组**至少保留一个文件**，不可被批量动作清空。
- 当一组内所有文件都被标记为「删除」时，执行层**拒绝执行该组**，界面提示「该组至少保留一份」。
- 用户可显式对某条执行「保留」来满足该约束。
- **验收**：批量勾选整组后执行，被自动保留组主并在界面提示；用户强制全删时该组被拒。

**FR-18 批量动作与二次确认（P0）**

- 批量动作作用于当前选中项；选中项跨组时，须按组分别校验 FR-11。
- 执行批量删除前弹出确认层，明确列出：**待删文件数、涉及组数、总字节数、落地方式（系统回收站 / 本机隔离区）**。
- 「同名不同内容」区的批量删除，确认层须**额外用告警色重申「这些文件内容不同」**，并要求二次确认（两次点击）。
- 「内容重复」区批量删除只需一次确认。
- **验收**：两类区的确认层强度不同；重名类需两次确认才能执行。

### 6.4 抑制机制

**FR-12 抑制黑名单（内容哈希）（P0）**

- 抑制项以**内容哈希**为键：`{ sha256, scopeRoot, scopeMode, createdAt, hitCount, samplePaths }`。
- `scopeMode` 取值：
  - `root`（默认）：仅在抑制时所在扫描根下生效；
  - `global`：对所有目录生效（用户显式选择时写入）。
- 扫描时命中抑制项的**整组**跳过，不进入结果区、不计入统计；但须在扫描摘要中报告「因抑制跳过 N 组」。
- 抑制项在**执行删除动作时同样生效**——被抑制的哈希不得出现在待删队列中（避免「提示时跳过、删除时却删掉」的矛盾，对齐 Czkawka 的排除项语义）。
- **验收**：抑制后重新扫描同一目录，该组不再出现；摘要显示跳过数量；抑制项不会出现在待删队列。

**FR-13 抑制清单与撤销入口（P0）**

- **入口位置（定版）**：检测页**顶部工具栏常驻**按键「抑制清单 (N)」，N 为当前抑制项数量；无抑制项时显示为「抑制清单 (0)」且可点击（展示空态）。
- 清单面板内容：每条显示**短哈希指纹**、样例文件名、作用域（当前根 / 全局）、抑制时间、**累计命中次数**、以及一个**「撤销」**按钮；面板顶部提供**「全部撤销」**。
- 撤销后该项立即从黑名单移除，下次扫描该组**重新提示**。
- 面板入口在主界面**不重复放置**（避免第二套抑制语义）；抑制清单是本功能唯一的撤销入口。
- **验收**：从检测页可打开清单、逐条撤销、全部撤销；撤销后重新扫描该组重新出现；抑制清单是唯一撤销入口。

### 6.5 交互与呈现

**FR-14 双击路径打开所在目录（P0）**

- 结果列表中的**文件绝对路径**双击后，在系统文件管理器中定位该文件（打开其所在目录并选中该文件）。
- 复用既有 IPC `app:reveal`（`shell.showItemInFolder`），不新造机制。
- 文件已不存在或路径不可访问时，给出**明确提示**（「文件已不存在或不可访问」），**不静默失败**。
- 该 IPC 需补路径边界校验（§6.6 FR-20）。
- **验收**：双击路径弹出系统文件管理器并定位到该文件；文件已删除时提示明确。

**FR-15 扫描进度与取消（P0）**

- 进度须分阶段可见：**扫描目录 → 大小分桶 → 局部哈希 → 全量哈希 → 汇总**。
- 每阶段显示：已处理数 / 总数、已读字节、当前吞吐、预计剩余。
- **随时可取消**，取消立即生效（不等当前文件算完），已完成的哈希结果保留在内存中供本次会话查看。
- 取消后界面回到「已取消」态，**不报告为完成**。
- **验收**：扫描中点击取消，状态变为「已取消」而非「完成」；进度数据与实际阶段一致。

**FR-16 结果列表虚拟化（P1）**

- 结果列表复用现有 `VirtualList`（`src/components/VirtualList.tsx`），十万级条目不打爆 DOM 与 IPC。
- 虚拟化**只影响渲染**，不截断数据：所有条目仍在内存中，动作作用于全量数据。
- **验收**：十万条结果滚动流畅；「保留全部」等批量动作作用于全部条目而非可见区。

**FR-17 统计与可回收空间（P1）**

- 扫描摘要：文件总数、总字节、耗时、分组数（内容重复组 / 同名不同内容组）。
- 可回收空间 = 各内容重复组 (份数 − 1) × 单份大小 之和；**同名不同内容区不计入可回收空间**（删除它们不省空间）。
- 明确区分「可回收空间」与「待删字节」两个数字，避免用户误以为删掉重名文件也能省空间。
- **验收**：可回收空间只由内容重复组贡献；删除待执行时显示待删字节。

### 6.6 持久化、安全与跨平台

**FR-19 持久化与审计日志（P1）**

- 抑制清单持久化到本机 `userData`（原子写：临时文件 + fsync + rename），格式与既有 `manifest.ts` / `journal.ts` 的写入方式一致。
- 操作审计日志记录：时间、动作类型、文件路径、组标识、结果（成功/跳过/失败）、失败原因。日志路径**脱敏**后写入事件流。
- 审计日志**只写本机**，不上传、不外发。
- **验收**：重启应用后抑制清单仍在；审计条目可追溯到具体动作。

**FR-20 权限与安全边界（P0）**

- 渲染层**不得**直接执行删除：所有删除请求经主进程校验后执行，主进程是唯一写入点。
- IPC 入参校验：删除与 reveal 的路径必须落在**本次扫描根目录**之内，且必须是扫描结果中真实存在的条目（不接受渲染层伪造路径）。
- 符号链接：扫描阶段跳过；删除前若目标已变为符号链接，**拒绝删除**。
- 日志脱敏：绝对路径在审计日志中按既有 `security.ts` 的脱敏规则处理，不落明文凭据。
- **验收**：伪造的路径请求被主进程拒绝并记录；扫描后被替换为符号链接的文件不被删除。

**FR-21 跨平台回收站行为矩阵（P1）**

- 明确三平台回收站可用性与降级路径：Windows 资源管理器回收站 / macOS 废纸篓 / Linux 回收站（`trash` 未安装或无 XDG trash 目录时降级本机隔离区）。
- 降级一律**明确告知**，不静默换目标。
- 网络盘 / SMB / 只读卷上的删除：默认**拒绝**并提示（回收站语义不可靠），用户可改为「仅标记不删除」。
- **验收**：三平台各自的落地方式与提示文案与矩阵一致；网络盘删除被拒绝。

## 7. 状态机

### 7.1 检测页状态

```
idle ──选择目录──▶ scanning ──▶ bucketing ──▶ hashing ──▶ ready
                       │            │            │          │
                       └────────────┴────────────┴──────────┤
                                                          ▼
                                                       acting
                                                          │
                            ┌─────────────────────────────┼─────────────┐
                            ▼                             ▼             ▼
                         done                        failed         cancelled
```

| 状态 | 含义 | 允许的动作 |
| --- | --- | --- |
| `idle` | 未选目录 | 选目录 |
| `scanning` | 遍历目录、采集元数据 | 取消 |
| `bucketing` | 按大小分桶 | 取消 |
| `hashing` | 局部哈希 / 全量哈希 | 取消 |
| `ready` | 结果已就绪 | 逐条动作、组级动作、批量动作、删除 |
| `acting` | 正在执行删除（二次校验 + 回收站落地） | 取消剩余项 |
| `done` | 动作完成，汇总结果 | 重新扫描 |
| `failed` | 扫描或执行失败 | 重新扫描 |
| `cancelled` | 用户取消 | 重新扫描 |

> **口径**：任一阶段被取消 → `cancelled`，不得置为 `done`；执行阶段存在失败项 → `failed` 并逐条列出失败原因，不得静默报完成（对齐本项目「失败不伪装成功」铁律）。

### 7.2 单文件动作状态

```
pending ──保留──▶ kept
   │
   ├──删除──▶ verifying ──通过──▶ trashing ──▶ deleted
   │              └──不通过──▶ skipped(已变更)
   │                            └──闸门拒绝──▶ blocked(介质异常)
   │
   └──下次不提醒──▶ suppressed
```

## 8. 关键流程

### 8.1 打开检测页并扫描

1. 主界面标题栏点击「重复文件检测」→ 切换到全屏检测页。
2. 选择目录 → 立即开始 `scanning`。
3. 遍历时跳过符号链接、跳过 0 字节文件、跳过小于阈值的文件；记录跳过计数。
4. `bucketing`：按 size 分桶，仅保留桶内 ≥ 2 个的组。
5. `hashing`：对候选逐个算首尾 64 KiB 局部哈希；仍相同的再算全量 SHA-256；超过 256 MiB 的标记「疑似」并停止读取。
6. 命中抑制黑名单的组直接跳过（FR-12），计入摘要。
7. 汇总为两个结果区，进入 `ready`。

### 8.2 处理一个内容重复组

1. 组默认标注「建议保留」的一条（FR-07 规则），不自动删除。
2. 用户点「保留此份，其余可删」→ 其余进入待删队列，可回收空间更新。
3. 用户点「删除」→ 该条进入待删队列。
4. 点「下次不提醒」→ 组哈希写入黑名单，该组立即从列表消失（可在抑制清单中撤销）。

### 8.3 执行删除

1. 用户点「执行删除」→ 确认层（FR-18）：数量、组数、字节数、落地方式。
2. **前置校验**：备份/自动同步是否在运行（FR-10）→ 运行中则拒绝并提示。
3. 逐条执行：
   a. **二次校验**（FR-09）：重算哈希 + 比对大小 + 校验文件身份；
   b. **闸门裁决**（FR-10）：`service.writeGate()` → 不放行则标记 `blocked` 并停止该条；
   c. **回收站落地**（FR-08）：系统回收站 → 失败则降级本机隔离区并告知；
   d. 符号链接复查（FR-20）：已变为符号链接则拒绝。
4. 全部完成 → `done`，输出汇总（成功 / 跳过 / 失败 / 被阻）与审计日志。

### 8.4 撤销「下次不提醒」

1. 检测页顶部点「抑制清单 (N)」→ 打开清单面板。
2. 面板列出全部抑制项（指纹、样例文件名、作用域、时间、命中次数）。
3. 单条「撤销」或顶部「全部撤销」→ 立即从黑名单移除并落盘。
4. 下次扫描该组重新出现在结果中。

## 12. 风险与待确认项

### 12.1 决策结论（已定版）

| # | 决策项 | 结论 | 理由 |
| --- | --- | --- | --- |
| 1 | 删除落地方式 | **系统回收站 + 删除前二次校验** | 删除不可逆是本项目最忌讳的失败模式；系统回收站符合行业惯例（Deskora 只进回收站），二次校验防住「扫描后被改动」。两者叠加后，误删需同时突破两道防线 |
| 2 | 重名不同内容类的默认动作 | **不预选任何删除项，整页告警** | 云盘四大厂一致把同名冲突当「保守合并」而非「重复」；这类文件的内容不同，删任一份都丢独有数据 |
| 3 | 「下次不提醒」的实现与撤销 | **内容哈希黑名单**；撤销入口为**检测页顶部工具栏常驻的「抑制清单 (N)」** | 哈希为键可天然覆盖整组（组内成员哈希相同），无需按路径逐条记录；抑制清单是唯一撤销入口，避免第二套语义 |
| 4 | 近似重复（pHash） | **本期不做**，P1 储备 | 需图像解码依赖，与「零第三方依赖」冲突；误判风险高于收益 |
| 5 | 撤销入口位置 | **检测页顶部工具栏** | 用户在同一页面内完成「抑制 → 发现需要撤销」的闭环，不跳页面；主界面不重复放置 |
| 6 | 抑制作用域 | 默认**当前扫描根**，可显式选「全局」 | 纯哈希全局抑制会跨目录隐藏合法重复；作用域化把影响面锁在用户预期的范围内 |

### 12.2 未决风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 大目录全量哈希耗时长 | 用户以为卡死 | 分阶段进度 + 吞吐 + ETA；提供「仅按大小分桶的快速模式」作为后续可选项 |
| Linux 无 trash 实现 | 回收站落地不可用 | 降级本机隔离区（可还原）并明确告知（FR-08、FR-21） |
| 网络盘 / SMB 回收站语义不可靠 | 误删 | 默认拒绝该场景的删除，提示「仅标记不删除」（FR-21） |
| 抑制过度导致重复文件长期不可见 | 用户以为已清理 | 清单显示累计命中次数；一键全部撤销 |
| 扫描期间其他程序修改文件 | 删掉的是另一个版本 | 二次校验 + 文件身份校验（FR-09） |
| 检测页与备份引擎并发 | 破坏 manifest / 断点 | 互斥 + 统一写入闸门（FR-10） |
| 同名判定在大小写不敏感文件系统上的歧义 | 误判为同名冲突 | 同名比较按文件系统语义归一化；仅作为告警类，不影响自动判定 |

### 12.3 待确认项（不阻塞开工）

- 「快速模式」（只做大小分桶，不算哈希，仅提示同名）是否值得作为附加档位——建议留待实现阶段再定。
- 审计日志保留期与轮转策略的具体天数。
- 本机隔离区（降级回收站）的容量上限与到期清理策略——建议对齐 `aut/recycle.ts` 的既有口径。

### 17.1 实现与规格的两处口径说明

1. **同名判定做了归一**（FR-05 / §5 / §12.2）：比较键为「同一父目录 + 文件名」，文件名先做 Unicode NFC 归一（NTFS 不做 Unicode 规范化，`café.txt` 的 NFC 与 NFD 形式在磁盘上是两个文件、对用户是同一个名字），再按文件系统语义折叠大小写（仅 Windows / macOS）。
2. **同名不同内容区在大小写不敏感的卷上天然稀疏**：同一父目录内**完全同名**的两个文件在 NTFS / APFS 上无法并存，因此该区的现实触发面主要是 Unicode 归一差异（NTFS）、大小写敏感卷上的 `Report.txt` 与 `report.txt`（Linux / 大小写敏感卷），以及后续可能扩展的「同主名不同扩展名」口径（本期未纳入，见 §12.3）。
