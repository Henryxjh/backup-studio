## 1. 需求分析（辩证）

### 1.1 需求合理之处

1. **源端重复是备份场景里最容易被忽略的成本放大器**。同一份 2 GB 的素材在源目录里有 3 份，用户的真实意图通常是「这份数据我有就行」；但备份工具会把 3 份原样搬进目标端，得到 6 GB 占用、3 倍复制耗时，以及 3 份需要独立维护的恢复路径。这份浪费在备份完成之前是**完全不可见**的。
2. **跨端同内容不同路径对用户而言就是重复**。源端 `doc/a.txt` 与目标端遗留的 `a.txt` 内容相同、路径不同，在计划器眼里这是「改名配对」（目标端改名对齐，零字节传输）；在用户眼里，备份前后的路径变了却没人告诉他。显式呈现这类关系，能消除「备份把文件搞乱了」的困惑。
3. **报告形态符合本项目既有立场**。本项目一以贯之的是「默认只读、写入须可解释、失败不伪装成功」（见 REQ-ENG-001 §3.2）。先出一份可审阅、可导出、可逐组确认的报告，再由用户决定是否改变备份行为，比直接替用户删文件更贴合这条主线。
4. **判定链路与现有计划器同源**。源端内部重复的判定本质就是 `planner.ts` 第五轮「按 size 分桶 → 同哈希分组」的推广，能力上已有八成地基，不需要引入第二套哈希判定逻辑——这一点直接关系到本项目反复强调的「避免两套判定逻辑漂移」（见 REQUIREMENTS-002-AUTO-SYNC.md §14）。

### 1.2 必须澄清和补强的点

| # | 补强点 | 说明 |
| --- | --- | --- |
| 1 | 「重复」必须锁定为字节级精确相同 | 判定口径为 SHA-256 全等。**近似重复 / 相似文件是另一个功能**：它需要额外的相似度算法、带来误判与额外依赖，也与本项目「I/O 成本高于 CPU 成本」的定位偏离。本期不做，且不在报告里给出「疑似」档位以免用户误当结论 |
| 2 | 扫描本身是重 I/O 操作 | 十万级目录全量哈希不可接受。必须 **size 分桶前置**：size 唯一的文件直接出局，只有同 size 桶内的候选才进哈希阶段。大部分目录里绝大多数文件 size 唯一，这一刀能砍掉绝大部分成本 |
| 3 | 历史哈希不得冒充当前哈希 | 源端 manifest 记录了历史 `sha256`，但**绝不能用它代替当前源端哈希**——否则同尺寸原地改动的文件会被误判为重复并被排除，造成漏备份。可复用历史哈希的前提与 `planner.ts` 第三轮一致：`size` 与 `mtime` **同时**吻合才可复用 |
| 4 | 哈希读取失败 ≠ 不是重复 | 单文件哈希失败必须标记为「判定失败」并排除在分组之外，不得因失败而被静默合并进某个组，也不得因失败而被当作「唯一副本」。失败清单需单独呈现 |
| 5 | 排除冗余副本会改变备份集的恢复语义 | 采纳排除后，恢复出的目录**不再与源端结构一一对应**：内容字节可完整还原，但被排除副本的路径与独立元数据（mtime、权限）不再还原。必须在采纳前明确告知，不得让用户在不知情的情况下改变恢复语义 |
| 6 | 排除名单必须同时作用于计划器的「孤儿 → 删除」判定 | 否则会出现「源端不再写入、目标端却被删掉」的自相矛盾：一旦某副本被排除，它在源端仍存在但不再参与复制，逻辑上不应再被当作「源端新增」而永久留在目标端；同时它也不能被当作孤儿删掉。这条是本需求与 `planner.ts` 最深的耦合点 |
| 7 | 目标端已存在的冗余副本如何处置，是本需求最大的风险点 | 目标端是用户的**恢复点**。若只让「冗余副本不再新增写入」，而目标端里早先备份的那份仍在，**空间根本没省下来**——这是本需求最容易做成「看起来有收益、实际没收益」的陷阱。要真正回收空间就必须动目标端，而动目标端需要先证明「另有内容完全相同且校验通过的副本存在」 |
| 8 | 源端文件一律不删 | 本需求不清理源端。源端删除是另一个功能（移动介质容灾、回收站治理都涉及删除语义），混在一起会让本需求的边界失焦。源端只读，是硬约束 |
| 9 | 规范副本的选取必须确定性 | 同一目录两次扫描必须得到同一份报告，否则报告不可复现、采纳结果不可预期。需要一条不依赖用户交互的默认规则，同时保留用户改选的能力 |
| 10 | 跨端重复的处置权归计划器 | 跨端同内容不同路径的**实际处置**已由 `planner.ts` 改名配对覆盖。本需求只负责**呈现**，不得重写一套配对逻辑，否则会与计划器漂移 |
| 11 | 报告规模可能极大 | 十万级源目录可能产生数万组重复。必须虚拟渲染 + 截断提示 + 可导出；且**截断只影响呈现，不影响后台判定**（沿用 `MAX_ACTIONS` 已确立的「仅截断预览」原则） |
| 12 | 扫描必须严格只读 | 探测与扫描阶段不得创建目录、不得写目标端、不得产生 `.part` 临时件。这与 REQ-ENG-001 的「探测阶段零写副作用」是同一条约束 |
| 13 | 排除名单的落盘与闸门的联动 | 排除名单写本机 `userData` 不经介质，不受写入闸门管辖；但「冗余副本不再写入」是**写入行为的改变**，闸门拒写时不得让用户以为「在备份」而实际没写 |
| 14 | 链接类与特殊文件的处理 | 符号链接默认不跟随（与 `scan.ts` 一致）；硬链接在同一内容组内只计一份**路径**、但其 inode 共享意味着删一份不影响另一份，需在报告中标注；零字节文件天然同哈希，须单独成组并明确「零字节文件全部互为重复」的语义，避免用户误删整个空文件集合 |

### 1.3 建议默认策略

| 项 | 默认值 |
| --- | --- |
| 判定口径 | 字节级精确相同：SHA-256 全等 |
| 扫描范围 | 已配对的源目录 + 目标目录；只读 |
| 判定顺序 | size 分桶 → 仅同 size 候选算 SHA-256 |
| 历史哈希复用 | 仅 `size` 与 `mtime` 同时吻合时允许，否则必须实算 |
| 报告形态 | 分组视图 + 可回收空间估算 + 可导出；虚拟渲染，预览超量截断但后台判定完整 |
| 规范副本（源端内部重复） | 默认取相对路径 POSIX 字典序最小者；允许用户在报告中改选 |
| 规范副本（跨端重复） | 以源端为准：源端那份是规范副本，目标端那份对齐到源端路径（由计划器改名配对执行） |
| 采纳动作 | 冗余副本**不再写入目标端**；**源端文件一律不删** |
| 目标端既有冗余副本 | 默认不动（仅报告）；如需回收，须先证明规范副本在目标端存在且 SHA-256 校验通过，再经逐项授权移入回收站（复用 `aut/recycle.ts` 的 ≥7 天机制）——见 §11 待确认项 #1 |
| 排除名单持久化 | 本机 `userData` 为权威；名单绑定**源端相对路径**，跟随源目录，不跟随目标介质 |
| 符号链接 | 默认不跟随 |
| 零字节文件 | 单独成组并明确标注，不默认采纳 |

## 2. 背景与目标

Backup Studio 当前的判定链路覆盖三类关系：**同路径内容更新**（覆盖）、**源↔目标同内容**（哈希去重，零传输）、**源端文件改名或移动**（改名配对，零传输）。这三类的共同前提是「源端与目标端一一对应」。

现实中大量目录并不满足这个前提：

- **源端内部重复**：同一份素材在源目录的不同路径下存在多份（如 `原图/` 与 `素材库/归档/` 各存一份）。这些文件全部被完整备份到目标端，源端占一份、目标端再占一份，且两份在恢复时都会被还原。
- **跨端同内容不同路径**：源端 `doc/a.txt` 与目标端遗留的 `a.txt` 内容相同。计划器会把它判为改名（目标端改名对齐），结果正确，但用户在界面上**看不到这件事发生过**，也无法回答「我到底有几份数据」。

目标是提供**统一、可审阅、可解释**的重复关系视图，并在此基础上提供**一条明确改变备份行为的安全通道**：让用户选择冗余副本不再进入目标端。

核心承诺有三条：**不删源端文件**、**判定口径精确不误判**、**改变备份行为前必须显式确认且可回退**。

## 3. 范围

### 3.1 包含

- 源目录内部的重复文件检测与分组
- 源目录与目标目录之间的跨端重复检测（内容相同、相对路径不同）
- 统一重复报告：分组视图、关系分类、判定依据、可回收空间估算、导出
- 规范副本选取（默认确定性规则 + 用户改选）
- 排除规则的采纳与持久化：冗余副本不再写入目标端
- 排除规则与计划器的耦合：孤儿删除判定必须识别排除名单
- 扫描进度、取消、大规模结果的截断与虚拟渲染
- 哈希失败清单的单独呈现
- 审计记录与日志

### 3.2 不包含

- **源端文件的删除或移动**。本需求对源端严格只读，源端清理需另立条目
- **近似重复 / 相似文件 / 感知哈希**（见 §1.2 第 1 条）
- **目标端内部重复的独立扫描**。目标端冗余仅在跨端比较中被顺带识别（见 §11 待确认项 #1），不提供独立的「只扫目标端」入口
- **目标端冗余副本的默认清理**。默认仅报告；回收需逐项授权 + 校验证明（待确认项 #1）
- **备份历史归档目录（`.backup-studio/history`）内部的重复扫描**。该目录按次记录、无保留期语义，不参与重复判定
- **磁盘空间占用分析、目录体积排行、文件类型统计**
- **内容比对之外的可回收性判定**（如「这个文件还有别处引用」）
- **跨配对、跨介质配对之间的全局重复视图**（本期仅单配对）
- **备份计划外的独立去重工具形态**。本功能挂在既有配对流程上，不提供脱离配对的通用去重入口

## 4. 术语

| 术语 | 定义 |
| --- | --- |
| 重复 | 两个及以上文件的内容 SHA-256 完全相同；不涉及路径、文件名、时间戳 |
| 重复组 | 一组互为重复的文件，共享同一内容哈希与同一文件大小 |
| 关系类型 | 重复组内副本的归属关系：`source-internal`（副本全在源端）/ `cross-side`（源端与目标端各有一份且相对路径不同） |
| 规范副本 | 重复组中被视为「应当保留并备份」的那一份；由源端目录结构决定 |
| 冗余副本 | 重复组内除规范副本以外的部分；被排除后不再写入目标端 |
| 排除名单 | 持久化的「哪些源端相对路径属于冗余副本」规则集合；绑定源目录 |
| 判定失败 | 文件无法完成哈希计算，无法参与重复判定；单独呈现，不合并进任何组 |
| 跨端重复 | 源端文件与目标端文件内容相同但相对路径不同；其处置由计划器的改名配对执行 |
| 可回收字节 | 若采纳排除后可避免写入目标端的字节数（不含目标端既有副本的清理收益） |

## 5. 功能需求

### 5.1 扫描与判定

#### FR-01 扫描入口与只读边界

- 扫描在既有配对上下文内发起：源目录与目标目录均取自当前配对，**不接受独立的、脱离配对的任意路径输入**（见 §3.2）
- 扫描全程只读：只允许 `stat` / `read` / 目录遍历；**不得创建目录、不得写入目标端、不得产生 `.part` 临时件**
- 目标端遍历跳过 `.backup-studio` 元数据目录；源端同名用户目录不被跳过（沿用 `scan.ts` 现有语义）
- 符号链接默认不跟随，计入「已跳过」统计
- 硬链接在报告中按路径逐条列出，并标注「同一 inode」，删除其一不影响其他（见 §1.2 第 14 条）
- 扫描可取消；取消后不产出报告，并明确告知「已取消」而非「完成」

#### FR-02 两阶段判定

- **阶段一（size 分桶）**：按文件大小分桶。size 桶内只有一个文件的，直接判定为「无重复可能」，**不进入哈希阶段**
- **阶段二（SHA-256）**：仅对 size 桶内成员数 ≥ 2 的候选计算 SHA-256
- 哈希计算复用既有并发实现（`hashFilesDetailed`），并发数随 CPU 核数自适应
- 阶段二可被取消，取消后已完成的哈希结果保留，报告标记为「不完整」并给出已扫描比例
- 大文件不因体积被跳过；与备份侧一致，哈希失败记入判定失败清单而非跳过

#### FR-03 历史哈希复用与新鲜度约束

- 源端文件可复用 manifest 中的历史 `sha256`，但**仅当 `size` 与 `mtime` 同时吻合当前源端状态时**允许复用
- 任一不吻合，必须实算源端当前哈希
- **禁止**使用目标端 manifest 的哈希代替源端当前哈希
- 跨端比较时，目标端哈希取自目标端 manifest 的记录值（目标端文件由本工具写入，其记录可信）；目标端文件不在 manifest 中时实算
- 复用与实算的来源差异必须在报告中标注，不混为一谈

#### FR-04 分组与关系分类

- 同一 SHA-256 的文件归入同一重复组，组内记录：内容哈希、文件大小、副本数、占用总字节、每个副本的相对路径、所属端、关系类型
- 关系类型至少区分：
  - `source-internal`：副本全在源端
  - `cross-side`：源端与目标端各有一份，且相对路径不同
- 同一分组内同时存在 `source-internal` 与 `cross-side` 副本时，以组为单位标注混合关系，不拆成多个组
- 源端与目标端**相对路径相同且内容相同**的文件不算重复——那是正常的已备份状态（哈希去重已覆盖），报告中不出现
- 零字节文件单独成组并显式标注「零字节文件互为重复」，不默认提供采纳入口

#### FR-05 规范副本选取

- 规范副本**以源端目录结构为准**：源端存在该内容时，源端那份是规范副本；源端不存在时（纯目标端残留）不产生规范副本，也不进入采纳范围
- `source-internal` 组的默认规范副本：相对路径 POSIX 字典序最小者
- 规则必须确定性：同一目录重复扫描得到同一规范副本
- 报告中允许用户改选规范副本；改选后重新计算该组的可回收字节
- `cross-side` 组的规范副本恒为源端那份；目标端那份**不作为可排除对象**，其对齐由计划器改名配对完成（见 §1.2 第 10 条）

### 5.2 报告

#### FR-06 统一报告

- 所有重复关系进**同一份报告**，不按关系类型拆成多份
- 报告至少包含：组总数、副本总数、涉及总字节、可回收字节估算、判定失败文件数
- 每组可展开查看逐条副本路径、所属端、字节数、mtime、判定依据（哈希实算 / 历史哈希复用）
- 报告可导出为本机文件（JSON 或 CSV），导出内容含全部组，不受界面截断影响
- 导出为只读产物，不含凭据；路径按既有脱敏规则处理（`security.ts`）
- 报告为快照语义：导出后源端发生变化不自动更新，需重新扫描

#### FR-07 规模与呈现

- 界面用虚拟列表渲染分组与副本，十万级结果不打爆 IPC（复用 `VirtualList.tsx`）
- 呈现层超量时截断预览并**明确提示已截断**；后台判定与统计始终基于全量，**截断只影响呈现**
- 分组默认按「可回收字节降序」排列，同值按内容哈希字典序稳定排序
- 复制副本数与总字节在组标题上直接可见，不依赖展开

### 5.3 处置与排除

#### FR-08 采纳与排除规则

- 采纳以**组**为单位：一组内的冗余副本整体进入排除名单，不支持只排除组内部分副本（避免出现「同一内容被拆成两半各自排除」的歧义）
- 采纳后，被排除的源端副本**不再写入目标端**
- **源端文件一律不删、不移动、不改名**
- 排除名单持久化到本机 `userData`，记录源目录标识与被排除的源端相对路径集合
- 排除名单**绑定源目录**，不随目标介质切换而迁移或失效
- 排除名单可整体撤销；撤销后下一次备份恢复正常复制
- 排除名单变更写入审计（见 FR-14）

#### FR-09 与计划器的整合

- 排除名单必须接入计划器的判定链，且**不得引入第二套哈希判定逻辑**
- 被排除的源端副本在计划阶段**不生成复制动作**，但在源端存在性统计中仍计入
- **孤儿删除判定必须识别排除名单**：被排除的源端文件不得被判定为「源端已消失」而生成删除动作；目标端对应的既有副本**默认保留**
- 该条与既有「孤儿哈希读取失败不生成删除动作」是同类保护，两者的失败语义必须一致：无法证明可安全删除时，一律不生成删除动作
- 排除名单变更后，已生成的旧计划立即失效，须重新扫描生成新计划（沿用 REQ-ENG-001 的「旧计划立即失效」语义）

#### FR-10 目标端既有冗余副本

- 目标端已存在的冗余副本**默认只报告、不处置**
- 如提供回收能力，须同时满足：①规范副本在目标端存在且其 SHA-256 实测校验通过；②用户逐项授权；③移入回收站而非永久删除，保留期 ≥ 7 天（复用 `aut/recycle.ts` 的 `moveToRecycle` / `ensureRoom`）
- 任一条件不满足即保留该副本并在报告中标注原因，**不得静默删除**
- 详见 §11 待确认项 #1

### 5.4 可靠性与安全

#### FR-11 错误处理

- 单文件哈希读取失败：标记为判定失败，**不参与任何分组**，不因失败而被当作唯一副本或非重复
- 判定失败清单单独呈现，并说明「这些文件未被判定」而非「这些文件不重复」
- 源端或目标端不可达：扫描中止并明确报错，不产出部分报告冒充完整报告
- 权限不足导致部分子树不可读：明确列出不可读子树并标注「覆盖不完整」，报告需可区分「完整扫描」与「部分扫描」
- 报告生成阶段的任何失败：不得呈现为「扫描完成，0 组重复」

#### FR-12 与容灾写入闸门的联动

- 扫描与判定全程不写目标端，不经过写入闸门
- **采纳排除**改变的是后续备份的写入行为，仍受 `service.writeGate()` 统一裁决；闸门拒写时排除名单照常生效，但界面须显示真实写入状态，**不得呈现为「正在备份」**
- 排除名单写本机 `userData`，不经介质，不受闸门约束
- 目标端介质处于 L2 隔离或卷健康无法判定时：扫描仍可只读进行（读侧不受阻），但不得采纳任何涉及目标端清理的处置
- 介质掉线：扫描中止并保留已完成的判定结果，重新扫描前不产出过期报告

#### FR-13 权限与安全

- 需要读取源目录与目标目录的权限；权限不足时明确标注「能力缺失」，不伪造扫描结论
- 路径规范化与目录穿越防护，沿用 `safePath` 语义
- 扫描范围内出现符号链接默认不跟随，不解析链接目标
- 不提权、不长期持有高权限；底层操作最小权限
- 报告导出内容遵循既有日志脱敏规则，不落明文凭据

#### FR-14 审计与日志

- 记录：扫描起止与覆盖范围、判定失败清单、报告导出、排除名单的采纳与撤销
- 审计写本机账本（`journal.ts`），遵循「本机权威、盘上辅助」的既有约定
- 日志脱敏；报告导出路径不泄露无关用户目录

### 5.5 交互

#### FR-15 界面与用户提示

- 主界面提供「重复文件」入口，展示报告摘要与分组列表
- 采纳前明确告知语义变化：恢复出的目录不再与源端结构一一对应，内容字节可还原，被排除副本的路径与独立元数据不还原
- 采纳操作需一次明确确认，确认文案列出将要排除的副本数与字节数
- 提供「撤销排除」入口，并说明撤销后下次备份会重新复制这些文件
- 判定失败、覆盖不完整、扫描中断等异常状态在界面上与「扫描完成」明确区分
- 空结果需明确显示「未发现重复」，不得显示成空白或报错

## 6. 状态机

```
空闲 → 扫描中 → 判定中 → 报告就绪 → 已采纳（排除名单生效）
```

异常分支：

| 触发 | 状态 | 恢复路径 |
| --- | --- | --- |
| 用户取消扫描 | 已取消 | 重新扫描 |
| 源端/目标端不可达 | 错误 | 介质恢复 → 重新扫描 |
| 权限不足 | 部分扫描 | 提权或排除不可读子树 → 重新扫描 |
| 判定阶段哈希失败（部分文件） | 报告就绪-不完整 | 失败清单呈现，不自动重试 |
| 介质掉线 | 中断 | 只读检测 → 用户确认 → 重新扫描 |
| 排除名单变更 | 旧计划失效 | 重新扫描 → 生成新计划 |

## 7. 关键流程

### 7.1 扫描与判定

选择配对 → 校验路径包含关系与权限 → 源端与目标端并行只读遍历 → 按 size 分桶 → 仅对 ≥2 成员的桶计算 SHA-256 → 按哈希分组 → 归类关系 → 生成报告。

### 7.2 采纳排除

用户查看报告 → 选择要排除的组 → 确认语义变化 → 写入排除名单（本机原子写）→ 旧备份计划失效 → 重新扫描生成新计划 → 新计划中冗余副本不生成复制动作 → 目标端既有副本按 FR-10 处置。

### 7.3 撤销排除

用户撤销 → 从排除名单移除对应路径 → 审计记录 → 旧计划失效 → 重新扫描 → 被撤销的副本恢复正常复制（目标端缺失时按普通复制处理，目标端已存在且内容相同则走哈希去重，零传输）。

### 7.4 与备份流程的关系

```
扫描 ──► 报告 ──► 采纳排除 ──► 排除名单 ──► 计划器 ──► 备份
   │                    │
   │                    └──► 排除名单接入孤儿判定（不生成删除动作）
   └──► 报告只读，不改变备份行为
```

## 8. 数据与持久化

| 数据 | 内容 | 位置 |
| --- | --- | --- |
| 排除名单 | 源目录标识、被排除的源端相对路径集合、创建时间、来源报告摘要 | 本机 `userData`（权威） |
| 报告快照 | 组、分组哈希、副本路径与端、字节、可回收字节、判定依据、判定失败清单、扫描覆盖范围与完整性标记 | 本机 `userData` 或用户指定导出路径 |
| 审计记录 | 扫描起止、报告导出、排除采纳与撤销 | 本机账本 `journal.ts` |
| 扫描进度 | 已扫描文件数、已判定数、剩余数 | 运行时内存 + 事件推送 |

- 排除名单与报告均**不写入目标介质**，避免污染备份集与恢复语义
- 排除名单与报告的写入遵循 `writeJsonAtomic` 的原子写模式，失败不产生半截 JSON

## 9. 非功能需求

| 维度 | 要求 |
| --- | --- |
| 性能 | size 分桶前置，size 唯一的文件零哈希；哈希并发随 CPU 自适应；十万级源目录的扫描可取消、可续扫（重新扫描优先复用已有判定缓存） |
| 可靠性 | 判定失败不误判；覆盖不完整必须标注；报告生成失败不得呈现为「无重复」；扫描全程零写副作用 |
| 一致性 | 判定口径为 SHA-256 全等，跨次扫描结果可复现；规范副本选取确定性 |
| 安全 | 只读扫描、路径规范化、防穿越、符号链接不跟随、日志脱敏、最小权限 |
| 兼容性 | 复用既有三平台能力矩阵语义；FAT32/exFAT 上仅依赖 read/stat 的能力不受平台限制 |
| 可用性 | 报告语义自解释；采纳前告知恢复语义变化；异常状态与正常完成明确区分 |

## 10. 验收标准

1. 对含重复内容的源目录执行扫描，报告正确列出重复组，每组副本数与总字节正确
2. size 唯一的文件不进入哈希阶段（可由哈希调用计数或日志验证）
3. 同内容不同路径的源端文件与目标端文件被归入同一组并标注 `cross-side`
4. 源端与目标端相对路径相同且内容相同的文件**不出现**在报告中
5. 单文件哈希读取失败时该文件进入判定失败清单，**不进入任何分组**，报告标注覆盖不完整
6. 同一目录连续扫描两次，报告内容与规范副本选取完全一致
7. 采纳排除后，被排除副本在下次备份中**不产生复制动作**
8. 采纳排除后，被排除副本在目标端**不产生删除动作**（孤儿判定识别排除名单）
9. 采纳排除**不删除、不移动、不改名任何源端文件**
10. 撤销排除后，被排除副本在下次备份中恢复复制行为；目标端已存在同内容副本时零字节传输
11. 目标端既有冗余副本默认不被处置；任何清理动作均先验证规范副本校验通过，且经逐项授权，失败时保留并标注原因
12. 排除名单变更后旧计划立即失效，须重新扫描才能开始备份
13. 扫描全程不创建目录、不写目标端、不产生 `.part` 临时件
14. 报告超量时界面截断预览并明确提示，导出内容仍为全量
15. 源端不可达或权限不足时，界面明确报错或标注「覆盖不完整」，**不呈现为扫描完成**
16. 报告可导出为 JSON/CSV，路径脱敏，内容不含凭据
17. 排除名单变更与报告导出均产生审计记录

| 8 | `.backup-studio/history` 与 `.backup-studio/aut-recycle` **均不参与重复判定** | 历史归档按次记录、无保留期语义，回收站条目是「已删除的受管项」，两者都不代表用户仍在使用的数据 | 纳入判定：会产生大量「可回收」假阳性 | FR-01；与 §3.2 保持一致 |
| 9 | 本期**不提供**脱离配对的「只扫源端」独立入口 | 与 §3.2 的范围声明一致，避免功能边界外扩；源端只在有配对时可查 | 提供独立入口：便于排查，但需要一套独立的目标根配置与边界校验 | §3.1 / FR-01；若评审要求，另立条目而非在本条目内扩范围 |

## 16. 实现落点

**状态：P0 已实现。** 独立测试见 `test/dup-finder.test.ts`；原生窗口取证与真机拔盘未做。

| 能力 | 落点 |
| --- | --- |
| 重复检测引擎 | `electron/engine/dup/detect.ts` — 两阶段判定：`scanTree` 结果按 size 分桶 → 仅同 size 候选算 SHA-256（`hashFilesDetailed`）；同相对路径的源/目标副本合并为一条逻辑副本 |
| 编排层 | `electron/engine/dup/index.ts` — `DuplicateFinder`：只读扫描、报告裁剪、采纳/撤销排除、导出、取消；状态与报告落本机 `userData/dup/` |
| 排除名单持久化 | `electron/engine/dup/exclusions.ts` — `ExclusionStore`，按源目录分组，`writeJsonAtomic` 原子写；每条记录带排除时的哈希与源端 mtime |
| 类型契约 | `shared/dup-types.ts` — `DupGroup` / `DupCopy` / `DupReport` / `DupExclusion` / `DupStatus` / `DupApi`（与 `shared/aut-types.ts` 同构） |
| 计划器接入 | `electron/engine/planner.ts` — `PlanInput.excluded`：被排除的源端副本不生成复制/更新动作；命中排除名单的孤儿**不生成删除动作** |
| 计划失效联动 | `electron/engine/service.ts` — `setExclusionProvider()` 注入名单来源；`invalidatePlan()` 使旧计划立即失效 |
| 哈希复用口径 | `electron/engine/hash.ts` 导出 `hashConcurrency()`，计划器与重复检测共用；源端哈希只复用排除记录、目标端哈希才复用清单 |
| 硬链接识别 | `electron/engine/scan.ts` — `ScannedFile.ino` |
| IPC | `electron/main.ts` — `dup:status` / `dup:scan` / `dup:adopt` / `dup:revoke` / `dup:export` / `dup:cancel`；`preload.ts` 同步白名单 |
| 界面 | `src/components/DuplicateFinder/` — 沿用 `AutoSync/` 面板结构，组列表走 `VirtualList.tsx` |
| 测试 | `test/dup-finder.test.ts`，并入 `npm run test` 与 `ci.yml` |

**与原规划的两处偏差**：

1. **FR-03 的哈希复用按端区分**。清单 `manifest` 里的 `mtimeMs` 记的是**目标端落盘时间**（复制过程不保留 mtime），因此它只能用于复用**目标端**文件的历史哈希；源端哈希一律实算，除非排除记录里存有源端自己的 mtime。这比原文「size 与 mtime 同时吻合即可复用」的表述更严格——照原文执行会让同尺寸原地改动漏判。
2. **FR-10 目标端冗余回收未实现**。待确认项 #1 尚未决议（默认只报告），因此本轮没有动目标端的删除通道，也就没有引入第二套回收站语义。

**未覆盖**：原生窗口下的面板交互；真机拔盘时的扫描中止与恢复；十万级目录的实际性能取证；网络盘上的扫描耗时。
