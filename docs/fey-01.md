## 1. 一句话描述

源端目录里只要有**两份内容完全相同的文件**（哪怕文件名相同、内容一致，是复制粘贴出来的），备份时**两份会一起被复制到目标端**；而且在「重复文件检测」页做过查重处理之后，情况反而更糟——目标端那份副本会**永远留着**，源端删了也不清理，甚至会出现**一份都没备份**的情况。

---

## 2. 现象

### 2.1 现象 A：重复副本被一并备份

源端子目录中存放 5 个完全一致的文件（同名 + 同内容）：

```
源目录/
├─ dir1/photo.jpg   ┐
├─ dir2/photo.jpg   │
├─ dir3/photo.jpg   ├─ 5 份内容完全一致
├─ dir4/photo.jpg   │
└─ dir5/photo.jpg   ┘
```

执行同步后，目标端被完整写入 **5 份**，没有任何合并、也没有任何提示。

实测计划输出（引擎级复现，调用仓库自带 `buildPlan`）：

```
计划汇总: {"totalFiles":5,"copy":5,"update":0,"rename":0,"delete":0,"skip":0,"bytes":20480}
  - copy	dir5/photo.jpg	源端新增
  - copy	dir4/photo.jpg	源端新增
  - copy	dir3/photo.jpg	源端新增
  - copy	dir2/photo.jpg	源端新增
  - copy	dir1/photo.jpg	源端新增
```

### 2.2 现象 B：查重之后目标端不再收敛

接着在「重复文件检测」页查重，命中 1 个内容重复组（5 个条目），并对该组执行「下次不提醒」（抑制）→ 再同步 → 源端删掉 `dir5/photo.jpg`（源端剩 4 个）→ 再同步。

**结果：目标端仍然是 5 个文件**，源端已经消失的那份副本始终没有被清理。

```
抑制清单展开为备份侧排除名单（exclusionPaths）: 5 条
  dir1/photo.jpg  dir2/photo.jpg  dir3/photo.jpg  dir4/photo.jpg  dir5/photo.jpg

严格镜像模式（mirror）:
  带排除名单: {"totalFiles":4,"copy":0,"update":0,"rename":0,"delete":0,"skip":4}
  对照组（不带排除名单）: {"totalFiles":4,"copy":0,"update":0,"rename":0,"delete":1}
    - delete	dir5/photo.jpg	源端已不存在，将永久删除且不留副本
```

对照组证明：**引擎本身会生成删除动作**，"目标端残留 5 份"是被查重产生的排除名单挡掉的。

> **注意（上游最新 `main` 的变化）**：上游 `9cc3663` 起，手动备份默认改为**非破坏性**（`syncMode: 'copy'`），目标端多余文件按设计保留（`retain` 动作）。因此在**默认模式**下"目标端还有 5 个文件"已是预期行为，**不再由排除名单造成**；但在 `mirror` / `mirror-archive` 严格镜像模式下，排除名单挡删的问题**依然成立**。
>
> 与模式无关、始终成立的是下面的**现象 C（静默漏备份）**，那才是这个缺陷最需要跟进的部分。

### 2.3 现象 C：抑制后首次同步，一份都不备份

如果先查重抑制、**再**做第一次同步（目标端原本是空的），这 5 个文件**一份都不会被写入目标端**（默认 `copy` 与严格镜像模式下都成立）：

```
计划汇总: {"totalFiles":5,"copy":0,"update":0,"rename":0,"delete":1,"skip":5}
  目标端最终文件数: 0（源端文件数 5）
```

统计里 `totalFiles:5` 照常计入，`copy:0`，界面上只呈现为 5 条「已按重复排除规则排除，不写入目标端」，容易被误读成"已经备份过了"。目标端连回收站副本都没有——这些文件**从未被写入过**。

---

## 3. 现状：代码是怎么走到这个结果的

### 3.1 备份引擎本来就不做"源端内部去重"（符合现有规格）

`electron/engine/planner.ts` 的哈希能力只用在**源端 ↔ 目标端**之间：把"源端新增文件"与"目标端孤儿文件"配对成改名动作（`planner.ts:211-219`、`:230-268`）。源端自己目录里的多个文件之间**从不做内容比对**，relPath 不同就各生成一条 `copy`。

这一点是写在规格里的既定边界，`docs/REQUIREMENTS-003-DUPLICATE-FINDER.md` §4.2 非目标明确写着：

> 与备份引擎的自动联动（备份时顺带查重）｜改变备份主线的语义与性能｜**不做**

以及 §4.1：

> 备份引擎只负责把源端镜像到目标端，不回答「目标端里哪一份是多余的」。

**所以现象 A 是"符合规格但反直觉"的行为，缺的是界面上的预期管理，不是引擎逻辑。**

### 3.2 真正的缺陷在"查重 → 备份"的接缝上

用户唯一能影响备份的查重动作是「下次不提醒」（抑制）。这条链路是这样的：

| 环节 | 代码位置 | 行为 |
| --- | --- | --- |
| ① 抑制写入 | `electron/engine/dup/index.ts:576-589` | 以**内容哈希**为键写抑制记录 |
| ② 记录整组路径 | `electron/engine/dup/index.ts:721-750`（`:735`） | `paths = group.entries.map(...)` —— 存的是**整组全部条目**，不是用户点的那条，也不是"保留的那一份" |
| ③ 展开成排除名单 | `electron/engine/dup/index.ts:694-710` | 换算成相对路径集合 → 整组 5 条全进名单 |
| ④ 注入计划器 | `electron/engine/main.ts` → `service.ts`（`setExclusionProvider` → `planBackup`） | `excluded: await exclusionProvider(sourceRoot)` |
| ⑤ 排除写入 | `electron/engine/planner.ts:105-115` | 命中的源文件**不生成写入动作**（只计入文件数） |
| ⑥ 排除删除 | `electron/engine/planner.ts:329-331` | 目标端孤儿若命中排除名单 → **不生成删除/保留动作**（该判断在 `copy` 模式的 `retain` 分支 `:344` 之前），注释写明"排除表示『这份内容由规范副本代表』，不是『可以删掉』" |

**问题就出在 ② 和 ⑥ 的组合上：**

- 排除名单的粒度是"整组路径"，连**规范副本（用户选择保留的那一份）**也一起被排除了 → 这一组内容**从此不写入目标端**（现象 C：静默漏备份，与同步模式无关）；
- ⑥ 把"不写入"扩大成了"不参与孤儿判定" → 在 `mirror` / `mirror-archive` 严格镜像模式下，目标端已经存在的副本被永久冻结，源端删了也不收敛（现象 B）；默认 `copy` 模式下则退化为"按设计保留"，不再由排除名单造成。

结果就是：查重本意是"告诉备份引擎这组内容由规范副本代表"，实现上却变成了"这一组内容从此不参与备份对账"。

### 3.3 现状定性

| 现象 | 现状定性 | 是否符合规格 |
| --- | --- | --- |
| A. 重复副本被一并备份 | 引擎按源端镜像复制，不做源端内部去重 | **符合** `REQUIREMENTS-003` §4.2；问题在于缺预期管理与提示 |
| B. 查重后目标端不收敛 | 抑制名单按整组路径展开，孤儿判定被一并豁免；**默认 `copy` 模式下该现象已是上游非破坏性语义的预期结果，严格镜像模式下才是缺陷** | 严格镜像模式下**不符合** `REQUIREMENTS-003` FR-11「每组至少保留一份」的跨端语义 |
| C. 抑制后首次同步漏备份 | 排除名单豁免写入，且统计口径未区分"已写入 / 已跳过" | **不符合**；属于静默漏备份，与同步模式无关 |

---

## 4. 影响

| 影响面 | 说明 |
| --- | --- |
| 静默漏备份 | 抑制后首次同步，目标端缺整组文件，用户看不到任何告警（现象 C） |
| 严格镜像下目标端不收敛 | `mirror` / `mirror-archive` 模式下，源端删除后目标端副本永久残留，备份链两端长期不一致（现象 B） |
| 冗余占用 | 目标端保留 N 份相同内容，容量与校验成本成倍增加（现象 A） |
| 排除粒度过粗 | 抑制一条即冻结整组，规范副本也不再受保护 |
| 用户无法自救 | 「抑制清单」面板看不出某条抑制影响了备份覆盖范围 |

---

## 5. 期望行为（修复方向）

1. **备份侧去重只作用于"源端内部"，且可控**：要么在计划阶段把内容一致的多份合并为一份，要么保持现状但**显式告知**"本次写入 N 份内容相同的文件"，并给出跳转「重复文件检测」页的入口。
2. **抑制名单只覆盖冗余副本**：规范副本（保留项）必须继续参与备份对账——这是漏备份的直接成因。
3. **"不写入"不等于"不参与孤儿判定"**：被排除路径若在目标端已存在、而源端已消失，应按当前 `syncMode` 的规则处理（`copy` 保留 / `mirror` 清理），而不是被整体跳过；若产品上确实要保留目标端副本，必须由用户显式选择，而不是由"抑制"这个动作隐式决定。
4. **抑制时明确告知影响范围**：确认层写明"该组 N 份文件将不再被备份到目标端（含从未备份过的副本）"。
5. **统计口径对齐**：计划汇总要把"已写入"和"因重复排除未写入"分开，界面不要让"跳过"看起来等于"已备份"。
6. **补回归用例**：`抑制 → 首次同步`、`抑制 → 源端删除 → 再同步` 两条路径都要断言目标端最终内容，且在 `copy` 与 `mirror` 两种模式下各跑一遍。
