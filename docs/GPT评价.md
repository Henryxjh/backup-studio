先说结论：

**Backup Studio 不只是一个普通的文件复制工具，而是一套以数据安全为核心的本地备份与单向同步系统。**

它试图解决几个传统备份软件容易处理不好的问题：

1. 重复备份造成大量无效磁盘写入。
2. 源文件改名后，目标端又多出一份重复文件。
3. 备份过程中拔掉移动硬盘，导致任务状态混乱。
4. 断点续传时重新复制整个大文件。
5. 镜像同步误删文件，造成不可逆的数据损失。
6. 目标磁盘自身存在健康问题，却仍然继续写入。

从 README 展示的设计来看，这个项目比较突出的地方是**将备份、同步、介质健康检查和写入许可控制整合在一个安全状态机中**。

以下先解析整体架构、核心算法、功能实现和目前的局限。需要区分的是：README 中的设计声明和测试覆盖，不等同于已经独立验证了所有实际运行效果。

## **一、项目定位与功能边界**

### **1. 它究竟是什么？**

Backup Studio 是一个 Windows / Linux 桌面端本地文件备份软件。

它不是传统意义上的双向同步工具，而是以源目录为权威、目标目录为备份副本的**单向镜像系统**。

## **核心工作模式**

**源目录**

用户原始数据，具有权威性

扫描 → 差异计划 → 安全检查 → 执行

**目标目录**

备份副本、索引、断点记录、历史归档

所有写入由容灾状态和写入许可共同约束

项目提供两种主要使用方式：

| 模式   | 工作方式               |
| ---- | ------------------ |
| 手动备份 | 用户选择目录、生成计划、确认后执行  |
| 自动备份 | 文件事件监听、差异对账、实时单向同步 |

这里有一个重要区别：

- 手动备份支持 Windows 和 Linux。
- 自动备份目前实际上只在 Windows 提供完整的卷级健康检查与写入能力。
- Linux 和 macOS 因缺少对应的卷级检测能力，自动备份采取默认只读策略。

### **2. 功能模块**

| 模块   | 主要能力                |
| ---- | ------------------- |
| 文件同步 | 新增、修改、删除、改名同步       |
| 哈希去重 | SHA-256 内容比对        |
| 复制引擎 | 多 Worker 并行复制       |
| 断点续传 | 1 MiB 分片校验和复用       |
| 介质容灾 | 拔盘检测、身份识别、恢复        |
| 数据保护 | 删除确认、历史归档、回收站       |
| 磁盘诊断 | NTFS、MBR、GPT、备份索引检查 |
| 自动同步 | 文件监听、去抖、差异对账        |
| 安全控制 | 统一写入闸门、隔离观察         |

## **三、核心算法解析**

这是整个项目最有技术价值的部分。

### **1. 哈希去重与改名识别**

核心文件：`electron/engine/planner.ts`

传统备份软件通常采用路径对比：

```
源目录：
  a.txt

目标目录：
  a.txt
```

当源端发生改名：

```
源目录：
  b.txt

目标目录：
  a.txt
```

传统方案可能直接把 `b.txt` 当成新文件复制，之后再删除 `a.txt`。

Backup Studio 则尝试通过内容哈希识别两者是同一份文件。

它的判断过程大致如下：

## **五轮差异判定**

1. **元数据快判**

   检查 manifest 中记录的文件大小、修改时间，完全一致就直接跳过。
2. **文件大小判断**

   同路径文件大小不同，直接判定需要更新。
3. **同尺寸哈希比较**

   对可能发生内容变化的文件计算 SHA-256。
4. **按文件大小分桶**

   新增文件只与大小相同的目标端孤儿文件进行潜在改名匹配。
5. **改名配对**

   内容哈希相同，旧路径消失，新路径出现，则判定为改名。

举个例子：

| 源端          | 目标端         | 结果 |
| ----------- | ----------- | -- |
| a.txt（内容 A） | a.txt（内容 A） | 跳过 |
| a.txt（内容 B） | a.txt（内容 A） | 更新 |
| b.txt（内容 A） | a.txt（内容 A） | 改名 |
| c.txt（新内容）  | 不存在         | 复制 |

这个方案的优点是：对于大量重复备份的数据，能够减少不必要的哈希计算和磁盘写入。

但这里我发现了一个需要优先处理的问题，后面会专门说明。

### **2. 分片断点续传**

核心文件：`electron/engine/copyWorker.ts`

默认分片大小：

# **1 MiB**

它不是传统意义上的简单偏移续传，而是逐块比较已有临时文件与源文件。

**假设一个 4 MiB 文件中断了**

1 MiB

正常

1 MiB

损坏

1 MiB

正常

1 MiB

正常

正常分片直接复用

只重写损坏分片

具体过程：

1. 打开源文件和 `.part` 临时文件。
2. 按 1 MiB 读取源文件。
3. 计算当前源分片 SHA-256。
4. 读取目标临时文件对应位置。
5. 对比两块数据。
6. 一致则不写入，不一致则重新写入。
7. 完成后重新计算整个临时文件的 SHA-256。
8. 验证通过才允许提交最终文件。

此外，还会检查源文件复制期间的大小、修改时间和变更时间，防止复制过程中源文件被修改。

**评价：这是一个比较扎实的断点续传实现。** 它不仅考虑了文件截断，也考虑了等长数据损坏。

不过，整文件回读校验仍然会产生额外的读取开销。它优化的是写入量，不意味着续传过程完全没有 I/O 成本。

### **3. 拔盘容灾机制**

核心文件：`service.ts`、`media.ts`、`journal.ts`

这是我认为项目最有特色的设计之一。

普通备份软件遇到移动硬盘拔出，通常只能抛出文件系统异常。

Backup Studio 做了更多处理：

- 每 700ms 探测一次介质。
- 连续两次探测失败，判定介质掉线。
- 停止继续向目标盘写入。
- 将断点保存在本机 userData。
- 保留介质身份信息。
- 重新插入后检查是否还是原来的设备。

## **拔盘恢复状态流程**

1. **正常备份**

   目标介质在线，任务正常执行。
2. **发现介质掉线**

   停止目标盘写入，保存本机事务账本。
3. **用户重新插入设备**

   只读检查介质可达性与身份。
4. **重新生成备份计划**

   旧计划失效，重新扫描源端与目标端。
5. **用户明确确认恢复**

   再次检查写入许可，使用分片校验恢复复制。

特别值得肯定的是：它没有设计成插盘后自动续传。

因为旧计划中可能包含删除操作。如果用户拔盘期间修改了源目录，直接执行旧计划就可能误删数据。

这是一个正确的容灾设计决策。

### **4. 自动备份引擎**

核心目录：`electron/engine/aut/`

这一部分与手动备份引擎相对独立。

自动备份不是简单地监听文件变化然后立即复制，而是采用：

**事件监听 → 去抖 → 差异对账 → 写入许可 → 原子复制 → 更新索引**

主要组件：

| 文件         | 职责        |
| ---------- | --------- |
| watcher.ts | 监控文件系统变化  |
| queue.ts   | 去抖与重试调度   |
| sync.ts    | 差异对账和同步调度 |
| copy.ts    | 原子复制及校验   |
| recycle.ts | 删除回收与恢复   |
| permit.ts  | 写入许可契约    |
| bridge.ts  | 对接容灾模块    |

这里有几个不错的设计：

- 默认不把目标端外部修改直接覆盖掉，而是暂停同步，等待人工处理。
- 自动删除可以关闭。
- 开启删除后，删除操作进入独立回收站。
- 默认保留七天，且支持容量限制。
- 替换已有文件时，先保留旧版本，再提交经过验证的新版本。
- 文件尚未稳定时延迟处理，避免复制正在写入的文件。

尤其是 `copy.ts`，它采用临时文件、完整哈希校验和最终原子提交的方式，避免把尚未复制完整的文件暴露为正式备份文件。

这比简单的 `fs.copyFile()` 更可靠。

### **5. 磁盘健康检测与写入闸门**

核心文件：`health.ts`、`media.ts`、`repair.ts`

这一部分让项目从单纯的文件备份工具，进一步发展成具有一定容灾诊断能力的软件。

它检查的内容包括：

| 检查项目    | 检查内容                  |
| ------- | --------------------- |
| 介质状态    | 是否可达、是否只读             |
| 文件系统    | NTFS 卷健康状态            |
| NTFS 脏位 | 是否需要文件系统修复            |
| 磁盘身份    | 是否发生设备替换              |
| MBR     | 签名及分区边界               |
| GPT     | 主备分区表及 CRC32          |
| 备份索引    | manifest 是否完整         |
| 文件内容    | 是否缺失、截断或哈希不一致         |
| 可靠性数据   | 系统提供的部分 SMART / 可靠性指标 |

需要特别说明：它不是完整的 SMART 诊断工具，也不能保证识别所有物理坏盘。

项目采用了一个比较重要的设计：

统一写入闸门

手动备份和自动备份共用写入许可判断。

**写入许可判断**

**L0 / 健康状态**

符合条件时允许写入

**L1 / 只读观察**

证据不足、卷需要修复等情况，阻止写入

**L2 / 隔离状态**

介质不可达、身份漂移、隔离等情况，禁止写入

注意：L0/L1/L2 是项目自身的风险分级，不是 Windows 或磁盘厂商的标准。

另一个值得肯定的地方是：人工修复入口目前主要用于只读预检、证据收集、关键扇区镜像和修复演练，并不直接执行分区表修复。

这实际上是一种比较谨慎的设计。

## **四、我发现的代码问题**

这部分是我认为比功能介绍更有价值的内容。

我直接查看了 `planner.ts`、`copyWorker.ts`、`service.ts`、`health.ts` 和自动同步相关代码，发现了一个比较严重的潜在数据一致性问题。

高优先级 · 建议立即修复

### **1. 哈希去重存在同尺寸文件误判风险**

位置：`electron/engine/planner.ts`

问题出在 `sameSize` 文件的哈希处理。

当前代码逻辑：

```
const memo = manifestFiles[src.relPath];

if (memo && memo.size === dst.size && memo.sha256) {
  return null;
}
```

它会在 manifest 已有哈希时，跳过源文件的实际哈希计算。

随后又使用 manifest 中的历史哈希填充源端和目标端的哈希结果。

这会产生一个逻辑问题：

假设：

**上次备份**

| 文件   | 内容 | 大小     |
| ---- | -- | ------ |
| 源文件  | A  | 100 KB |
| 目标文件 | A  | 100 KB |

manifest 记录：

`SHA256(A)`

**这次备份**

用户修改了源文件：

| 文件   | 内容 | 大小     |
| ---- | -- | ------ |
| 源文件  | B  | 100 KB |
| 目标文件 | A  | 100 KB |

实际应该更新

但是当前算法可能得到：

- 源端哈希：历史记录 A
- 目标端哈希：历史记录 A
- 两者相同，判定跳过

**结果：源文件内容已经改变，但备份计划可能认为不需要更新。**

这不是性能问题，而是数据正确性问题。

修复方向：

1. manifest 的哈希只能作为历史证据，不能同时替代当前源端和目标端的实际内容。
2. 源文件元数据发生变化时，必须重新计算源文件哈希。
3. 目标端哈希也必须有独立的有效性依据。
4. 对比结果不确定时，应当采取更新或拒绝执行，而不是直接跳过。

建议补充测试：

- 相同大小、修改时间改变、内容改变。
- 相同大小、源文件内容不变、仅修改时间改变。
- 目标端被外部修改，但大小不变。
- manifest 正常但目标文件损坏。

这是我建议首先修复的地方。

### **2. 计划列表存在 20000 条截断问题**

位置：`planner.ts`

代码：

```
const ordered = [...important, ...identical]
  .slice(0, MAX_ACTIONS);
```

其中：

```
const MAX_ACTIONS = 20000;
```

问题是：最终动作列表被截断，但是统计数据仍然按照完整文件集合计算。

如果实际需要执行的操作超过 20000 条，可能出现：

- 统计显示需要复制 25000 个文件。
- 实际计划列表只有 20000 条。
- 剩余操作没有进入计划。

如果执行阶段直接消费这个列表，就会造成备份不完整。

建议：

- 将计划数据与 UI 展示数据分离。
- 支持分页或分批执行。
- 如果不支持完整计划，必须直接拒绝执行，不能静默截断。

### **3. 自动备份和手动备份的能力边界需要明确**

目前自动备份的安全机制比手动备份更严格，特别是在卷健康检测方面。

但用户容易产生一个误解：

以为手动备份也具备自动备份同等程度的所有保护。

实际上，两者虽然共用部分介质检测与容灾能力，但自动同步还有自己的索引、回收站和冲突处理机制。

建议在 UI 中明确标识不同模式的保护能力。

## **七、最终结论**

我对这个项目的总体评价是：

**它的设计目标已经超过普通文件备份工具，正在向一个具备介质容灾能力的本地数据保护系统发展。**

尤其是三个设计值得保留：

- 基于内容哈希的差异识别。
- 基于本机事务账本的拔盘恢复。
- 手动与自动备份共用的写入安全闸门。

不过，我不会建议现在就把它作为唯一的重要数据保护手段。

最重要的原因不是缺少功能，而是我发现了哈希判定上的潜在正确性缺陷。对于备份软件来说，**宁可多复制一次，也不能把已经变化的数据误判为未变化。**

另外，备份本身不等于完整的数据保护。真正重要的数据仍然应该遵循 3-2-1 备份原则，至少保留独立的第三份副本。

## **八、下一步建议：进行一次真正的代码审计**

目前这次解析已经覆盖了主要架构和关键算法，但还没有逐行审查全部源码，也没有实际运行仓库测试。

我建议下一步进行一次针对性深度审计，重点检查：

1. 是否存在其他导致数据丢失、漏备份或误删除的问题。
2. 所有写入操作是否都受到写入闸门保护。
3. 原子提交在 Windows 和 Linux 下是否真正可靠。
4. 断点续传是否存在边界条件错误。
5. 自动同步的回收站和事务恢复是否存在竞态。
6. Electron IPC 是否存在路径注入或权限绕过。
