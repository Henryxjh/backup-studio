# Backup Studio PR 审查清单

本页规定 Backup Studio 的 PR 审查细则。`SKILL.md` 保留原则与流程入口。审查必须以对应 SHA 的实际代码与 Diff 为依据，并沿调用链核对规格、状态变更与测试断言。PR 标题、描述和提交信息只提供背景，不能单独作为审查依据。

## 1. 审查前置条件

> **每次开始新的 PR 任务，都必须重新检查本地与远程仓库状态，不得沿用上一次任务的检查结果或审查结论。** 旧版本的审查结论、旧版本的 Approve、旧版本的合并授权都不自动适用于新版本。

| 核对 | 开始审查前必须确认 |
| --- | --- |
| ☐ | 已确认 PR Head SHA，审查所读的代码、测试和 Diff 与该 SHA 一致。记录对应的 PR Base SHA。 |
| ☐ | 本地审查工作区干净，无未提交、暂存或未跟踪的改动。发现改动时，保留现场，先解决审查依据的隔离问题。 |
| ☐ | 已取得最新 PR Diff，核对文件清单、重命名与删除项。若 Diff 被截断，补齐遗漏再开始。 |
| ☐ | 已取得 Base SHA 与 Head SHA 两侧的 CI 状态，记录检查名、运行链接（若有）和实际运行 SHA。无运行记录时明确记为 `Not run`，查不到时记录证据缺口。 |
| ☐ | 已确认 PR 仍为 `open`。Head 或 Base 变化时重新确认审查依据并评估哪些结论需要重验。 |

## 2. 审查维度清单

逐项标记已核对、待确认或不适用。不适用时给出原因。表中模块是检查入口。跨层改动要追踪到真实调用方和受影响的未修改代码。

| 模块 | 核对 | 检查点与判据 |
| --- | --- | --- |
| 全局范围 | ☐ | **01 目标是否清晰**。用规格或已确认的需求说明 PR 应改变的行为与非目标，例如查重抑制只影响检测页提示。 |
| 全局范围 | ☐ | **02 Diff 是否符合预期**。从入口走到最终行为，确认每项承诺都有实现，并检查删除、覆盖、跳过、重试的行为是否符合预期。 |
| 全局范围 | ☐ | **03 是否修改不相关文件**。核对全量文件清单，逐项确认附带的配置、文档、锁文件及格式变更是否有任务依据。 |
| 引擎 `electron/engine/` | ☐ | **04 是否引入重复实现**。核对正常删除与恢复对账是否复用同一删除判据，容量展示与闸门是否按同一份去重清单统计。 |
| 引擎 `electron/engine/` | ☐ | **05 是否违反现有架构**。确认 `dup/` 不越界改变备份计划，自动同步与手动备份的写入仍受现有闸门裁决。 |
| 引擎 `electron/engine/` | ☐ | **06 是否有逻辑错误**。检查删除阶段推进、`txId` 幂等、账本和索引的合并优先级、结案条目过滤及任务状态是否一致。 |
| 引擎 `electron/engine/` | ☐ | **07 是否遗漏边界条件**。核对容量恰好到上限、孤儿与未决占用、同名换版、长文件名、大小写敏感卷和重复恢复等相关分支。 |
| 引擎 `electron/engine/` | ☐ | **08 是否缺少异常处理**。检查 I/O、权限、解析、锁定、写入失败是否按语义处理并往上传递，例如只有 `ENOENT` 才能表示文件不存在。 |
| 引擎 `electron/engine/` | ☐ | **09 是否可能损坏或丢失数据**。核对归档和删除意图先于删除落盘，崩溃后可安全恢复，`uncertain` 保留证据，清理保护仍被引用的归档，容量超限时阻止新删除且不静默淘汰旧副本。 |
| 主进程 IPC `electron/main.ts`、`electron/preload.ts` | ☐ | **10 是否引入安全风险**。核对 `app:reveal` 由主进程授权并按生命周期撤销。检查路径身份、`realpath` 落点、联接与符号链接、Windows 设备语法及 ADS 的校验是否仍有效。删除与还原须在主进程复核写入授权及实际写入目标。 |
| 渲染层 `src/` | ☐ | **11 是否引入不合理的性能开销**。检查虚拟列表是否按真实滚动视口挂载行，打开回收站是否额外读取全部归档做全量哈希。还原前的必要校验需保留。 |
| 共享契约 `shared/` | ☐ | **12 是否影响兼容性**。核对 `types.ts`、`dup-types.ts`、`aut-types.ts` 与主进程、preload、界面的字段和状态一致。涉及账本、索引格式时检查升级前无 `txId` 或哈希基线的旧记录。 |
| 测试 `test/` | ☐ | **13 是否需补测试或文档（测试）**。确认回归用例通过生产入口覆盖相关分支，并断言文件实体、账本、索引和用户可见结果。缺少任一关键断言时指出要补的行为。 |
| 构建与发布 `.github/workflows/` | ☐ | **08、10、12、13 的发布检查**。核对失败是否中止发布、权限是否收敛、预期平台与产物是否齐全，以及 `ci.yml`、`release.yml`、`release-demo.yml` 的触发与门禁改动是否需要同步使用说明。 |
| 依赖与配置 `package.json`、锁文件、TypeScript / Vite 配置 | ☐ | **14 是否增加不必要的依赖**。核对已有 Electron / React / TypeScript / Vite 能力能否满足需求，新依赖是否进入正确的运行或开发范围，锁文件、打包配置与构建产物是否吻合。 |
| 规格与维护文档 `docs/` | ☐ | **13 是否需补测试或文档（文档）**。核对用户能看到的行为、升级兼容、闸门规则及尚未消除的数据安全窗口是否如实记录。 |

匹配测试时，以审查 SHA 的 `package.json` 为准。核对 `npm test` 是否实际跑到 `engine`、`auto-sync`、`write-gate`、`recycle`、`transaction-recovery`、`dup`、`reveal-authority` 和 `recycle-crash` 对应入口。脚本前序失败时，后续未执行的套件不能记为通过。

## 3. 风险分级与判定标准

每条发现必须分级。等级按实际影响和可验证的失败条件判定。

| 等级 | 定义 | Backup Studio 示例与分级理由 |
| --- | --- | --- |
| Critical | 严重安全问题、数据损坏、不可恢复的破坏 | 删除事务清理掉唯一归档副本，且原文件已删。用户已无任何副本可恢复，属于不可恢复的数据丢失。 |
| High | 核心功能错误、严重兼容性问题 | Windows 上统一转小写把大小写敏感卷的两个真实目标目录合并，回收站重建会串读账本，破坏核心恢复范围。`QuarantineStore.list()` 把索引损坏或权限错误吞成 `[]` 也属 High，用户失去正常恢复入口并误以为隔离区为空。 |
| Medium | 重要边界条件或明显质量问题 | 查重页的虚拟列表脱离真实滚动视口，大结果集不能正确按可见范围渲染，影响查看与性能，尚无证据表明它直接破坏文件数据。 |
| Low | 轻微缺陷或维护性问题 | 假设新增回收站诊断日志漏带 `txId`，但异常仍准确上报、事务和可见状态仍正确。影响限于定位单条事务的成本。 |
| Informational | 建议，不构成阻止合并的问题 | 现有测试已覆盖失败分支且断言充分，建议为两个相近的回收站用例增加注释说明验证对象。无可观察缺陷。 |

## 4. 发现记录模板与历史样例

每条发现使用稳定编号。Critical 用 `C1`、`C2`，High 用 `H1`、`H2`，同一问题有可独立核实的子项时用 `H1a`、`H1b`，Medium 用 `M1`、`M2`、`M3`。Low 与 Informational 可用 `L1`、`I1`。同一发现跨轮保留编号，不拿已结案编号标记无关问题。

| 必填字段 | 填写要求 |
| --- | --- |
| 风险等级 | `<稳定编号> · <Critical / High / Medium / Low / Informational>` |
| 文件路径 | `<仓库相对路径>`，跨层发现可补充相关路径 |
| 行号或代码位置 | `<审查 SHA 上的行号或函数与分支>`，展示时用 `文件:行号` |
| 问题描述 | `<实际行为与预期行为的差异>`，附 Diff、调用链、日志或测试断言。证据不足时标记「待确认」并写明缺什么。 |
| 影响范围 | `<受影响的入口、环境、用户或文件数据>` |
| 复现条件 | `<前置状态、输入或故障时点与观察结果>`，不适用时写明理由 |
| 建议修复方式 | `<符合现有架构的最小行为修正与回归断言>` |
| 是否阻止合并 | `<是 / 否>` 和依据，待确认时说明放行前还须核对的证据 |

以下是专项加固期间的历史发现。位置用函数或分支标记以便追踪。阻止合并栏按发现当时的状态填写。

| 字段 | C1 恢复时删除同路径的新版本 | H1b 现存索引行不按账本结案状态过滤 |
| --- | --- | --- |
| 风险等级 | `C1` · Critical | `H1b` · High |
| 文件路径 | `electron/engine/service.ts` | `electron/engine/recycle.ts`、`electron/engine/service.ts` |
| 行号或代码位置 | `reconcileDeletes()` 恢复待执行删除的路径及 `intent-persisted` 阶段的原文件删除分支 | `listRecycle()` 读取现存索引行的分支，以及 `listRecycleBin()` 传递结案集合的接线 |
| 问题描述 | 删除意图按路径记录。恢复按该路径删除时没有核对当前内容是否为旧归档对应的版本。 | 列表已过滤账本中带 `settled` 的行，却未用同一结案状态过滤普通索引残留行，导致两侧合并后已结案项重新显示。 |
| 影响范围 | 手动备份回收站删除事务。归档只有旧内容，同路径新内容被误删后无副本可恢复。 | 手动回收站列表。已还原或已彻底删除的条目被呈现为待处理，核心恢复视图与权威账本不一致。 |
| 复现条件 | 归档已生成，在意图落盘后、删除前中断任务。把目标文件换成等长的新内容并恢复任务。旧实现会删除从未归档的新版本。 | 创建带 `txId` 的回收条目。把账本标为 `settled: 'restored'`，保留同 `txId` 的普通索引行且无待收尾操作意图。重新列出回收站时，旧实现仍显示该条目。 |
| 建议修复方式 | 删除前以 SHA-256 核对当前文件与归档基线。不符或无基线时转 `uncertain` 并停止删除。回归同时断言新文件保留、旧归档完好且任务未报完成。 | `listRecycleBin()` 传递已结案 `txId` 集合，`listRecycle()` 过滤普通残留行。用例覆盖显式结案集合和直接传入已结案账本行两种接线，同时保留有操作意图的待收尾证据。 |
| 是否阻止合并 | **是**。恢复路径可不可逆地删除未归档数据。 | **是**。与核心还原流程相连的列表错误会把已结案条目当作待处理。 |

## 5. CI 基线判定流程

1. 优先取得 PR Base SHA 和 PR Head SHA 的运行结果。记录运行或检查链接、实际运行 SHA、触发方式、工作流与失败步骤、平台、Node 版本及锁文件。若 PR 工作流测的是合成合并提交，注明其 SHA 与合入上下文，不能把它标成 Head SHA 的独立运行。
2. 对齐失败项和执行条件。对比同一套件、断言、错误特征及相关 Diff，尽可能在可比环境中分别验证两侧。若当前 `main` 已前移，把它的历史 CI 当作补充证据，不能替代 Base SHA 的记录。
3. 将每项失败归入下表并记录证据与处置。PR CI 红灯本身不足以证明是 PR 修改引入的。`main` 也有红灯时，仍须判断本次 Diff 是否引入额外失败或扩大影响。

| 分类 | 判断依据 | 处理动作 |
| --- | --- | --- |
| PR 新引入的失败 | 可比条件下 Base 对应项通过而 Head 失败，日志与代码或对照验证把失败归因到 Diff。若 Base 已失败，但 Head 多出可归因的新失败，也单独记录。 | 作为 PR 发现登记，修复后用同等检查或相应回归验证最新 Head。破坏必需检查或核心功能验证时阻止合并。 |
| `main` 基线已经存在的失败 | Base SHA 同项同因失败，且未发现该 Diff 引入或加重此失败。 | 记录失败项与 Diff 是否相关，尽可能本地复现，检查对应历史 CI 运行。不得擅自修改无关业务代码或测试来消除红灯。若影响本次 PR 核心功能验证，仍须阻止合并或要求额外验证，在证据补齐前不放行。 |
| 环境、依赖或基础设施导致的失败 | 日志表明失败来自 runner、网络、下载或依赖环境，且没有证据表明 PR 的依赖、脚本或配置引入了该故障。 | 保留错误细节，在可比环境验证相同 SHA。必需检查、核心功能验证的证据未补齐时继续阻止合并。 |
| 无法确认来源的失败 | 缺少 Base 对应运行、日志不可用、执行条件不同，或现有证据无法区分三类来源。 | 标记「待确认」，记录缺口并补查历史、日志或执行对照验证。若影响门禁或本次核心功能验证，继续阻止合并。 |

| CI 状态 | 记录口径 |
| --- | --- |
| `Success` | 对应检查实际执行并成功。记录粒度须与证据一致。 |
| `Failure` | 检查失败，按前表分类。 |
| `Pending` | 已排队或运行中，尚无结论。 |
| `Cancelled` | 检查取消，未完成验证。 |
| `Skipped` | 检查有记录，但因条件未执行。 |
| `Neutral` | 检查报告中性结论，未提供成功验证。 |
| `Not run` | 没有该检查的运行记录，例如工作流没有自动触发、也未手动运行。 |

**不得把未触发描述成 CI 通过。`Skipped` / `Pending` / `Cancelled` / `Neutral` / `Not run` ≠ 通过。** 按检查汇报状态。单个运行成功不足以证明所有条件步骤都已执行。本地验证需单列环境、SHA 与结果，不得改写 GitHub CI 状态。

## 6. 阻止合并判定

| 必须阻止合并的情形 | 解除条件 |
| --- | --- |
| 存在未解决的 Critical 或 High，例如可不可逆地误删文件、主进程路径授权越界或回收站结案状态错误。 | 主代理逐条核实并安排修复。每条有回归用例固定，复审确认最新 Head 的修复及验证结果。 |
| 缺陷虽未达 Critical / High，仍破坏本次明确的验收要求或必要安全边界。 | 记录具体违反的条件，经修复与验证后解除。Informational 和个人偏好不能作阻断依据。 |
| 必需检查未满足，或本次核心功能因失败、未执行、结果无法归因等原因缺少验证证据，包括基线已有失败。 | 取得与本次变更匹配的结果。额外验证与必需检查的处理按合并门禁执行。 |
| 与数据安全、删除及还原授权等核心边界有关的疑点尚待确认，且缺失证据令安全性无法判定。 | 标记「待确认」，明确核验项，补足证据后重新判级和判断阻断状态。 |

## 7. 审查原则与反模式

| 应该做 | 不应该做 |
| --- | --- |
| 优先指出可证实的缺陷，如删除对账推进错误、隔离区索引读失败被呈现为空。 | 为增加发现数量制造意见，或把个人编码偏好描述成 Bug。 |
| 在现有引擎、IPC、共享契约与渲染层边界内提出最小修复。 | 要求与现有架构不一致的重构，或顺带要求无关的代码风格调整。 |
| 按行为影响评估，单文件改动也追到必要的调用链、状态持久化和回归用例。 | 因文件少、Diff 短而降低审查标准。 |
| 对所有 PR 作者及贡献者使用相同的证据和等级标准。 | 按身份、资历或仓库权限调整要求。 |
| 证据不足就标记「待确认」，注明缺少的平台、日志、调用路径或用例。 | 把猜测写成已确定的回归，或直接沿用他人结论。 |

- **给规格外联动打补丁。** PR #2 把「查重抑制」接到备份排除名单，导致可能连规范副本也跳过，严格镜像也不能收敛。规格 §4.2 未授权该联动。处置是按规格整条移除，使抑制回到「下次不提醒」。不得把调整排除粒度或做与现有架构不一致的重构列为必修缺陷。[合入复审记录 §18](../../../../docs/REQUIREMENTS-003-DUPLICATE-FINDER.md#18-合入复审与缺陷修复2026-11-21)
- **隐去残余风险。** 例如同一 inode 在最后一次复核与 `unlink` 之间仍可被原地写入。未消除的窗口要在代码注释和文档中写明触发条件与影响，不得宣称已关闭。`process.exit` 回归只证明受测的进程崩溃情形，不能扩称真实断电、拔盘或其他文件系统语义已验证。
- **把刻意不修和遗漏混为一谈。** 列表阶段不对全部归档做全量哈希，打开回收站时只检查大小并如实呈现基线。恢复对账和索引重建校验哈希，实际还原有基线时严格核对内容。列表阶段的同大小外部篡改可能到还原时才被发现。**这是有意的性能取舍，不是遗漏。** 未实现的行为另行记录是否需要修复，不能用性能取舍为其背书。

## 8. 独立只读复审与后续轮次

1. 每个 PR 的关键工作流安排独立只读 Reviewer，给出绑定本轮 Head SHA 的 `VERDICT: FAIL` 或 `VERDICT: PASS`。`FAIL` 表示还有必须修复的 Critical 或 High。`PASS` 表示在所审范围内未发现此类未解决问题，同时记录其他阻断项、待确认项与残余风险。正式审批和合并另按对应门禁执行。
2. 每轮由主代理回到代码、Diff、调用链和测试逐条核实，再按发现编号派工。复审结论是核验线索，不得未经核实直接派工。争议或证据不足的条目标记「待确认」并注明缺口。
3. 每个 Critical / High 的修复必须用回归用例固定。复审逐条记录发现编号、对应测试文件和用例、关键断言及验证结果。数量用「旧例数 → 新例数（新增或调整 N 条，列出覆盖场景）」表达。例如专项加固中 `test/dup.test.ts` 为 `45 → 71`（新增 26 条，含索引异常分类与写入闸门相关错误透传），PR #2 合入复审另有 `25 → 37`（新增 12 条）的记录。各数字对应各自的历史基线，不能拼成连续序列。[专项加固记录](../../../../docs/TODO.md) · [PR #2 修订记录](../../../../docs/REQUIREMENTS-003-DUPLICATE-FINDER.md)
4. 第二轮及以后以「上一轮审查 Head → 当前 Head」的实际修复 Diff 收窄范围，只复核实际改动及其直接受影响的调用链与回归。例如第三轮只复核第二轮那 6 处改动。按稳定编号逐条核对修复、遗漏和新引入的问题，记录已修复、未修复或待确认。不得直接沿用上一轮结论。与本轮修复无关的既有阻断项仍应保留，直到有证据解除。
5. 每轮收尾记录本轮 SHA、范围、未关闭发现、已验证项、CI 基线结论及残余风险。实际实现或审查依据变化时，重新核对受影响的结论。
